# PRD-03 検証フロー

作成日: 2026-08-17
ステータス: ドラフト（レビュー待ち）
前提: [PRD-00](./00-product-definition.md) / [PRD-01](./01-onboarding-auth.md) / [PRD-02](./02-milestone-management.md)

対象画面: 02 / 05 / 06 / 19 / 43 / 44 / 45 / 46 / 46b / 46b（達成・連続強調）/ 75 / 76

---

## 1. この領域が担うこと

ユーザーが証跡を提出し、サーバーが達成/未達成を判定するまで。**課金の正当性はここで決まる**（PRD-00 §1.1）。

判定が緩ければペナルティが機能せず、厳しければ誤課金が発生する。本 PRD の中心はこの閾値をどこに置くかである。

---

## 2. 実行モデル

### 2.1 判定はサーバーが行う

クライアントの「達成しました」という申告は信用しない（PRD-00 §3.2）。クライアントの役割は**証跡の取得と送信**に限られる。

| 検証方法 | クライアントが送るもの | サーバーが判定すること |
|---|---|---|
| 写真 | 撮影した画像 | 指定された撮影対象が写っているか |
| 出発 | 現在地の座標と精度 | 基準地点から指定距離以上離れているか |
| 到着 | 現在地の座標と精度 | 指定地点の半径内にいるか |
| コード | 読み取った値（+ 撮影画像） | 登録済みコードと一致するか |

### 2.2 v1 では検証は常にユーザーの操作で始まる

自動達成は提供しない（PRD-00 §2.3）。ユーザーが締切前にアプリを開き、検証を実行する必要がある。したがって**リマインダーの到達性が達成率に直結する**（PRD-01 §5）。

### 2.3 判定のタイミング

即時に返す。45（検証失敗・再試行）が「認識できませんでした / 洗面台が写っていません」と理由を提示し、締切までの残り時間（00:11:48）と未達成時の金額（¥500）を出す構成になっているため、**判定は送信直後に完了している必要がある**。非同期のキューに載せて後で通知する設計は取れない。

写真の画像認識に数秒かかることを前提に、44 の「送信」から 46 / 45 までの間に待機状態が要る（**現行 UI に待機画面が存在しない**、§10 #1）。

## 3. 検証方法別のフロー

### 3.1 写真

```
02 案内「洗面台を撮影してください / カメラを起動」
   ↓
43 撮影（ガイド枠 + 撮影対象名「洗面台」）
   ↓
44 プレビュー「送信 / 撮り直す」
   ↓ 送信
（待機）→ 判定
   ├ OK → 46 検証結果（達成）
   └ NG → 45 検証失敗・再試行「もう一度撮影 / あとで」
```

- 43 は四隅にガイド枠を持ち、撮影対象名を表示する
- 撮影対象は作成時に選択したもの（75 / 58b）。58b が「選んだ写真が検証画面で見本として表示されます」と述べている通り、**見本の提示も 43 の要件**である

撮影対象は **75 のリストを正とし、拡張する**（2026-08-17 決定。PRD-02 §3.1 の積み残し）。現行 75 は12種で、カバーできる習慣が限られている。

38f（就寝準備をする）が持つインライン選択「ベッド / 寝室 / 洗面台 / その他」は 75 と粒度が合わない古い草案なので、75 に統一する（§11 #6）。

**「その他」は設けない。** 画像認識は何が写っているべきかが定義されていないと判定できず、自由入力では未達成の理由も説明できない。撮影対象は必ず列挙されたもののいずれかに限定する。

#### 判定の型

対象によって必要な判定の種類が違う。実装コストが大きく異なるため、型で分けて段階的に増やす。

| 型 | 判定内容 | 難易度 |
|---|---|---|
| **物体** | その物が写っているか | 低。一般的な物体検出で足りる |
| **状態** | 物が特定の状態にあるか（空のシンク、整えたベッド、消灯した部屋） | 高。「シンクがある」だけでは判定にならず、状態の評価が要る |
| **数値** | 表示された数字を読む（体重計） | 中。OCR が必要。読めた数値の妥当性判断も要る |

**v1 は「物体」型のみを提供する。** 状態・数値型は Phase 2 とする。

#### 選択 UI への影響

対象が増えるため、75 は検索とカテゴリ絞り込みを持つ現在の構成が前提になる（既に「ベッド、洗面台、ジム…」の検索欄とカテゴリチップを持っている）。カテゴリは現行の4つ（部屋 / 水まわり / 外出 / 食事）から**7つ**（水まわり / 寝室・部屋 / 運動 / 食事・栄養 / 学習・仕事 / 家事 / 外出）に増える（§11 #7）。

### 3.2 位置（出発 / 到着）

```
05 位置検証
   地図 + 目標地点「エニタイムフィットネス渋谷」+ 現在地からの距離「120m」
   + 半径円
   ↓「現在地で検証」
（取得 → 判定）→ 46 / 45
```

- v1 はフォアグラウンド取得のみ。「現在地で検証」を押した時点の座標で判定する
- 距離の表示はリアルタイムに更新する（120m のように現在の距離が出ている）
- 滞在時間は扱わない（PRD-00 §4.2）

### 3.3 コード

```
06 コード検証
   「プロテインのバーコードを読み取ってください / バーコード・QRコードに対応」
   + ライトを点ける
   ↓ 読み取り成功
（照合）→ 46 / 45
```

- 事前に 76 で登録したコードと照合する
- 読み取りはクライアント側で行うため、**読み取り値だけを送ると偽装できる**（§4.4）

## 4. 真正性 — どこまで防ぐか

### 4.1 「カメラ直撮りを強制できない」とは何か

ブラウザで画像を入手する経路は2つある。

| 経路 | 挙動 |
|---|---|
| `<input type="file" accept="image/*" capture="camera">` | `capture` は「カメラを開いてほしい」というブラウザへの**ヒント**であり、仕様上は無視してよい。実際デスクトップブラウザでは通常のファイル選択が開く |
| `getUserMedia` + canvas | カメラ映像をその場で取得する。UI 上にアルバムを開く手段が存在しなくなる |

SwitchMe は後者を使う（§4.3 #1）。これで**通常の操作でアルバムの写真を提出することはできなくなる**。

それでも次の2つは防げない。

- **カメラ入力の差し替え** — 仮想カメラ（OBS 等）を入れると `getUserMedia` はその映像を返す。ブラウザから見て実機のカメラと区別が付かない
- **クライアントコードの改変** — JavaScript はユーザーの手元で動いており、開発者ツールから送信処理を書き換えて任意の画像を送れる

サーバーに届くのは HTTP リクエストのバイト列でしかなく、「これが本物のカメラセンサーから来た」という証明は付いていない。**これが「強制できない」の意味**である。

ネイティブアプリでも原理は同じで、アプリを改造すれば同じことができる。違いは手間の大きさであって、質的な差ではない。

したがって**設計の目的は「防止」ではなく「割に合わなくすること」**になる。ペナルティは ¥100〜¥50,000 であり、仮想カメラの導入や JS の改変にかかる手間がこれを上回れば、経済的な合理性が消える。

### 4.2 判定は素直に行う

画像認識は「洗面台が写っている確信度 0.87」のようなスコアを返す。達成とみなす閾値を1つ決める。

**判定に特別なバイアスはかけない。** 「疑わしきは達成にする」といった扱いは、閾値が二重になって挙動を説明できなくなるうえ、「疑わしい」を実装上定義できない。閾値は1つ置き、運用開始後に実データで調整する。

誤判定への備えは、判定側ではなくその周りで行う。

- **再試行が締切まで無制限**（§5）なので、1回の誤判定がそのまま課金になることはない。角度や明るさを変えて撮り直せる
- 失敗時は理由を提示する（45「洗面台が写っていません」）ので、何を直せばよいかが分かる
- それでも納得できない場合は 65 の異議申し立てで個別に対応する（PRD-04）

初期閾値は判定モデルの選定時に決める（§10 #7）。

### 4.3 写真の緩和策

**v1 で採用するもの**

| # | 対策 | 防げるもの |
|---|---|---|
| 1 | `getUserMedia` によるカメラ取得のみを提供し、ファイル選択（ギャラリー）の経路を UI に置かない | 保存済み画像の安易な提出 |
| 2 | サーバー発行の nonce を検証セッションに紐づけ、その場で撮った1枚だけを受け付ける | 使い回し |
| 3 | 撮影から送信までの時間を制限する（提案: 5分） | 事前に撮った画像の温存 |
| 4 | 提出画像のハッシュを保持し、同一・ほぼ同一の画像の再提出を検出する | 毎日同じ写真を出す |
| 5 | 撮影時刻とサーバー時刻の乖離を検出する | 時刻偽装 |

**採用しないもの**: 撮影時に画面のランダムコードを一緒に写させる方式は、真正性は上がるが毎日の操作としては重すぎる。ペナルティ額に対して過剰。

**残るリスク**: 仮想カメラの差し込み、クライアントコードの改変は防げない。これは受け入れる（§4.1）。

### 4.4 位置

Geolocation API はデバイスの位置サービスに依存し、開発者ツールやエミュレータで座標を偽装できる。

**v1 で採用する緩和策**

- `coords.accuracy`（精度）を検証し、極端に良すぎる値・悪すぎる値を弾く
- 直近の検証位置との時間差・距離から、物理的に不可能な移動を検出する
- サーバー側で受信時刻を記録し、クライアントの主張する時刻を信用しない

IP ジオロケーションとの突き合わせは、モバイル回線では基地局の位置がずれるため**採用しない**（誤検知が多く、正当なユーザーを未達成にしてしまう）。

### 4.5 コード

登録済みの値と一致するかしか見ないため、**同一商品なら誰の手元のものでも通り、バーコードを撮影した画像でも通る**（PRD-00 §4.4）。これは手段の性質として受け入れる。

一方、**クライアントが読み取り値だけを送る構成では、値を直接送信するだけで検証を突破できる**。これは手段の性質ではなく実装の穴なので塞ぐ。

**決定（2026-08-17）**: 読み取ったフレームの画像をサーバーに送り、**サーバー側で再デコードして判定する**。画像は判定後に破棄し、**保存するのは読み取り値のみ**とする。

これにより 25 の「コード: 保存しない」の開示を変えずに、値の直接送信を防げる。ただし**証跡が画像として残らない**ため、48 課金明細の証跡欄はコード検証の場合「読み取った値と一致 / 不一致」の記録だけになる（§7.3）。

## 5. 再試行（45）

- 「認識できませんでした」+ 理由（「洗面台が写っていません」）+ 締切までの残り時間 + 未達成時の金額
- 「もう一度撮影」で 43 に戻る / 「あとで」でホームに戻る
- **締切までは何度でも再試行できる**（回数制限を設けない）

回数制限を設けない理由: 制限は正当なユーザーだけを罰する。暗い部屋・手ブレ・画角のずれで数回失敗するのは通常の使用であり、そこで打ち切ると誤課金になる。

ただし画像認識のコストは実費として発生するため、**レート制限（提案: 30秒に1回）**を設ける。連続送信を抑えるだけで、ユーザー体験には影響しない。

## 6. 検証できない状態（19）と課金の可否

### 6.1 UI は「課金する」前提で作られている

19 は「位置を取得できません」に対して、位置=オフ / ネットワーク=オフライン / 省電力モード=オンの内訳を示し、**「このまま期限切れ ¥500」「検証期限まで 00:11:42」**と表示する。免除を約束していない。

### 6.2 決定: 検証できないことを理由に免除しない

**理由**: 「位置情報をオフにしておけば課金されない」が成立すると、ペナルティの仕組みが根本から崩れる。そして**意図的なオフと不可抗力（圏外・端末故障）をサーバー側で区別する手段がない**。

**§4.1 の「迷ったら達成側に倒す」との関係**: あの原則は**提出された証跡を判定するとき**に適用される。証跡が1つも提出されていない場合には適用されない。判断の材料が無い以上、達成側に倒す根拠も存在しないためである。締切はそのまま適用し、例外は §6.2 の表の経路で個別に扱う。

代わりに以下で救済する。

| 状況 | 救済 |
|---|---|
| 一時的な検証不能 | 19 が締切前に警告し、復旧手段（「設定を開く」）を提示する。締切まで時間があれば自力で回復できる |
| 誤課金だと考える場合 | 65 問い合わせ（異議申し立てを兼ねる）で個別に対応する。PRD-04 の範囲 |
| 端末の紛失・長期の通信途絶 | 一定期間通信が無ければ全マイルストーンを自動停止する（PRD-00 §7.2 #4）。**未実装** |

3つ目は短時間のオフラインとは別の問題であり、**v1 に必要**。判定期間は要決定（§10 #4）。

### 6.3 19 に足りないもの

19 は状態を提示するが、**この状態がいつから続いているかを示さない**。締切直前に初めて気づく構成では手遅れになる。事前リマインド（24 設定/通知の「15分前・1時間前」）の時点で権限やネットワークの状態を確認し、問題があれば通知に含める（PRD-06）。

## 7. 証跡の保存

### 7.1 現行の保持期間（25 設定/プライバシー）

| 種別 | 保持期間 |
|---|---|
| 位置 | 90日 |
| 撮影写真 | 30日 |
| コード | **保存しない** |

「検証データを削除」でユーザーが任意に削除できる。

### 7.2 課金明細の「証跡」と矛盾する

48 課金明細は「判定 / 検証 / 支払い / 状態 / **証跡**」を表示する。証跡が消えた後の明細をどう表示するかが未定義である。

さらに深刻なのは**異議申し立てとの関係**。写真の証跡は30日で消えるが、異議申し立ての期限が定義されていない。**証跡が無い状態で異議を受けても、こちらは判断材料を持たない**。

**決定（2026-08-17）**

1. 異議申し立ての受付期間を**課金から30日以内**とし、写真の保持期間と一致させる
2. **証跡の削除は可能とする。** 「検証データを削除」を実行したら、保持期間内であっても削除する

自宅周辺の GPS 履歴や自室の写真は個人データにあたり、個人情報保護法はユーザーに利用停止・消去を求める権利を認めている。削除を塞ぐ設計は取らない。

**帰結**: 削除すると、その課金について**確認や再審査を求める材料が双方から失われる**。削除の確認時にこれを明示する。

> 削除すると、過去の課金について確認や再審査を求めることができなくなります。

未確定の課金に関わるデータまで即時削除してよいかは、会計上の証憑保持義務との兼ね合いがあるため**法務確認の対象**とする（§10 #5）。既定の挙動は「削除可能」とする。

### 7.3 コード検証の証跡

**決定（2026-08-17）: 画像は保存しない。**

§4.5 の通り、判定はフレーム画像をサーバーへ送って再デコードするが、**画像は判定後に破棄する**。25 の「コード: 保存しない」の開示をそのまま維持できる。

| データ | 扱い |
|---|---|
| 登録済みコード（76 で登録） | マイルストーンの設定として保存する（照合に必要） |
| 検証時に読み取ったフレーム画像 | サーバーで再デコードした後に**破棄** |
| 検証時の読み取り値 | **保存しない** |
| 判定結果（一致 / 不一致）と時刻 | 保存する |

**帰結**: 48 課金明細の証跡欄は、コード検証の場合「一致 / 不一致」の記録のみになる。写真・位置に比べて証跡が薄く、異議申し立て時に提示できる材料が限られる。これは開示の正直さを優先した結果として受け入れる。

## 8. 結果表示

### 8.1 達成（46）

ホームに戻った上にモーダルを重ねる構成。

- 「起床確認 / 達成 / 5日連続 / 過去7日間の記録（曜日ドット）」+ OK
- 背後のホームが更新されている（完了リストに「起床確認 ・ 07:42 に達成」が追加、残り件数が減る）

**連続強調版**（46b 検証結果（達成・連続強調））は「5 日連続 / 自己ベスト 8日 / 起床確認 を達成」と、ストリークを主役にした別バリエーション。**どちらをいつ出すかが未定義**（§10 #5）。

### 8.2 未達成（46b）

- 「朝の準備完了 / 未達成 / 07:30 · ¥300 課金」
- 背後のホームの完了リストに「朝の準備完了 ・ 未達成 ¥300」が追加される

**この画面が出るタイミングに注意が必要**。未達成の確定は締切到達時であり、ユーザーの操作起点ではない。アプリを開いていない時に確定した未達成をどう見せるかは、通知（PRD-06）と初回起動時の扱いの問題になる。46b は**アプリを開いた時にまとめて提示する**設計と読める。

### 8.3 評価依頼（84 / 85）との関係

`ui.pen` の NOTE「評価依頼モーダルの表示条件」より、**検証結果（達成）を閉じてホームに戻った直後**に重ねる。検証中・検証失敗の直後には出さない。詳細は PRD-06。

## 9. 受け入れ基準

### 9.1 判定

- [ ] クライアントが送るのは証跡のみで、達成/未達成の判断結果を送らない
- [ ] 送信から判定結果の表示まで、待機状態が表示される
- [ ] 判定に失敗した場合、理由・締切までの残り時間・未達成時の金額が表示される
- [ ] 締切までは回数無制限で再試行できる
- [ ] 30秒あたり1回を超える連続送信が抑制される

### 9.2 真正性

- [ ] 写真の提出経路にギャラリー選択が存在しない
- [ ] サーバー発行の nonce に紐づかない画像が受け付けられない
- [ ] 撮影から5分を超えた画像が受け付けられない
- [ ] 過去に提出したものと同一の画像が達成と判定されない
- [ ] 位置検証で、直前の検証位置から物理的に不可能な移動が検出される
- [ ] コード検証で、読み取り値のみを送信しても達成にならない（§10 #3 の決定に依存）

### 9.3 検証不能・証跡

- [ ] 権限オフ・オフラインを理由に未達成が免除されない
- [ ] 19 が締切前に、検証できない原因と復旧手段を提示する
- [ ] 未確定の課金・未クローズの異議申し立てに関わる証跡が削除できない
- [ ] 課金から30日以内は、48 の証跡が参照できる
