# PRD-01 オンボーディング・認証

作成日: 2026-08-17
ステータス: ドラフト（レビュー待ち）
前提: [PRD-00 プロダクト定義とスコープ](./00-product-definition.md)

対象画面: 30 / 31 / 32 / 33 / 12 / 12b / 34 / 35 / 13 / 36 / 60 / 62 / 61 / 14 / 18

---

## 1. この領域が担うこと

初回起動から**最初のマイルストーンが動き出すまで**を担当する。この区間の設計目標は2つある。

1. **課金されうるサービスであることを、課金が発生する前に理解させる**（33 が担う）
2. **最初の1件を作らせる**。マイルストーンが0件のユーザーは、このプロダクトの価値を一度も受け取っていない

この2つは競合する。理解を求めるほど離脱し、離脱を避けるほど「知らないうちに課金された」という事故に近づく。本 PRD の判断はこの緊張を軸にしている。

## 2. 導線

### 2.1 確定している遷移

各画面のボタンから確定できるもの。

```
30 スプラッシュ（セッション復元）
  ├ セッションあり → ホーム（01 / 18）
  └ セッションなし → 31

31 ウォークスルー 1/3「目標を決める」        ─ スキップ ┐
32 ウォークスルー 2/3「AIが自動で検証」      ─ スキップ ┤
33 ウォークスルー 3/3「できなければ課金」    ─ はじめる ┘
                                                        ↓
12 ログイン / 12b 新規登録  ←→  34 パスワードリセット → 35 メール確認待ち
                                                        ↓
13 権限リクエスト（すべて許可して次へ / あとで設定する）
                                                        ↓
36 セットアップ完了「最初のマイルストーンを作りましょう」
                                                        ↓
60 オンボ 目標選択（7種のプリセット / 自分で作る / もっと見る → 21）
                                                        ↓
38a〜38f 具体入力（PRD-02 の範囲）
                                                        ↓
62 オンボ 作成完了 ─ ホームへ / もう1つ作る
                                                        ↓
61 オンボ カード登録の案内 ─ カードを登録する → 14 / あとで登録
                                                        ↓
                                                    ホーム
```

### 2.2 Web v1 でログインを 33 の直後に置く理由

PRD-00 §2.2 の通り。ネイティブでは匿名アカウントで先に進める設計だが、**Web ではブラウザに識別子を永続化できないため、最初にログインを要求する以外の選択肢がない**。

ウォークスルーの前ではなく後に置くのは、「何のサービスか」を知る前に認証を求めると離脱するため。33 まで見せてからログインさせる。

### 2.3 未確定: 13 の「2/3」が何のステッパーか

13 権限リクエストの右上に `2/3` の表示がある。3ステップの2番目だが、1 と 3 が何かを示す画面が存在しない。

| 解釈 | 1 | 2 | 3 |
|---|---|---|---|
| A | ログイン | 権限 | 初回マイルストーン作成 |
| B | ログイン | 権限 | カード登録 |
| C | ウォークスルーとは独立したセットアップの3段階 | 権限 | — |

**A に決定**（2026-08-17）。カード登録を3番目に置くと（B）、ステッパーが「カード登録まで終わらないと完了しない」と宣言することになり、§6 の「初回だけカードなしで作らせる」方針と矛盾する。A なら 36 → 60 →（作成）で 3/3 が閉じる。

```
1/3 ログイン（12 / 12b）
2/3 権限リクエスト（13）
3/3 最初のマイルストーン作成（60 → 38x → 62）
```

**`ui.pen` への画面追加が必要**: 12 / 12b に `1/3`、60 に `3/3` のステッパー表示を加える。

## 3. 認証

### 3.1 提供する手段（12 / 12b）

| 手段 | v1 | 備考 |
|---|---|---|
| Google | ○ | 返信先メールが取れる |
| Apple | ○ | 「メールを非公開」の場合 `@privaterelay.appleid.com`。**Apple Developer の Email Communication にドメイン登録と SPF 公開が必要**（未対応なら返信が届かない） |
| メール + パスワード（8文字以上） | ○ | 12b の表示より |
| X | **提供しない**（2026-08-17 決定） | X の OAuth はメールを返さない設定がありうる。返信先メールを取得できない唯一の経路 |

**X を外した理由と影響**: PRD-00 §5.5 の通り、65 問い合わせが異議申し立て窓口を兼ねており「登録メールアドレスへ返信します」と約束している。X 連携ユーザーはこの約束の外に出る。X を外したことで、**v1 のすべてのユーザーが返信可能なメールアドレスを持つ**ことになる。

これに伴う変更:

- `ui.pen` の 12 / 12b から「Xで続ける」ボタンを削除する
- 65b（問い合わせ・メール未登録）は **v1 では不要**になる。ただし Apple の「メールを非公開」で `@privaterelay.appleid.com` への送信が失敗する場合の受け皿としては残る余地がある（§3.1 の Apple の行を参照）。PRD-05 で最終判断する

### 3.2 セッションの永続性

**v1 の最重要要件。** Safari の ITP により、サイト未訪問が数日〜1週間続くと localStorage も Cookie も破棄される。破棄された時点でユーザーは自分のアカウントに到達できなくなるが、**課金はサーバー側で動き続ける**。

したがって以下を満たすこと。

1. セッションが切れた状態でアクセスしたとき、**必ず 12 ログインに到達できる**（白画面やエラーで止まらない）
2. 再ログイン後、既存のマイルストーンと支払い方法にそのまま到達できる
3. ソーシャルログインの場合、同じ Google / Apple アカウントで同一ユーザーに解決される（メールアドレスの一致だけに依存しない安定した識別子を使う）
4. セッションが切れていても、**メール経由でカードの停止・退会に到達できる経路を用意する**（課金通知メールからの導線）

4 は現行 UI に存在しない。**新規設計が必要**（PRD-06 通知と合わせて扱う）。

### 3.3 パスワードリセット（34）・メール確認（35）

- 34: メールアドレスを入力 → 再設定リンクを送信。**送信完了の状態表示が画面上に存在しない**。35 メール確認待ちを流用するか、34 に完了状態を追加する
- 35 の「メールアプリを開く」は **Web では動作が保証されない**（`mailto:` はデスクトップブラウザで何も起きない場合がある）。v1 では「再送する」を主導線とし、「メールアプリを開く」は出さないか、モバイルのみ表示する
- **メール + パスワードで登録した場合、メール確認を必須とする**（2026-08-17 決定）。課金するサービスとして、到達可能な連絡先を持たないアカウントを作るべきではない
- Google / Apple 経由の場合は、認証時点で提供元がメールアドレスを検証済みのため**追加の確認は行わない**
- 未確認の状態でどこまで進めるかは、以下とする
  - 12b でアカウント作成 → 35 メール確認待ち → 確認完了までオンボーディングを進めない
  - 確認リンクの有効期限切れ・再送は 35 の「再送する」で処理する

## 4. 権限リクエスト（13）

### 4.1 現行 UI はネイティブ前提

現行の 13 は「位置 / 常に許可」「カメラ / 許可済み」「通知 / 許可する」の3項目を並べ、「すべて許可して次へ」で一括許可する構成になっている。**これは Web では成立しない。**

| 項目 | 現行表示 | Web v1 での実態 |
|---|---|---|
| 位置 | 常に許可 | **「常に許可」は存在しない**。Geolocation はフォアグラウンドのみ |
| カメラ | 許可済み | `getUserMedia` の権限。事前に一括では取れない |
| 通知 | 許可する | **PWA としてホーム画面に追加されていないと iOS では受け取れない** |
| — | すべて許可して次へ | **ブラウザには一括許可の API がない**。各権限はユーザー操作を起点に個別に要求する必要がある |

### 4.2 Web v1 での再設計

13 は「一括許可の画面」から「**これから何を求めるかの予告と、個別に許可させる画面**」に変わる。

- 位置: 「検証のときだけ現在地を使います」。**常時取得しない**ことを明示（現行の「常時撮影・常時位置取得はしません」の一文はそのまま活きる）
- カメラ: 「写真・コードの検証で使います」
- 通知: PWA インストールが前提であることを説明し、§5 の導線につなぐ
- 各行にボタンを置き、押したときに実際のブラウザ権限ダイアログを出す
- 「あとで設定する」は維持する。**権限を拒否したままマイルストーンを作れてしまうと、検証できないまま課金される**ため、作成時に検証方法と権限の対応をチェックする（PRD-02 で扱う）

### 4.3 権限が無い状態で締切を迎えた場合

19（検証エラー）が「位置 オフ / ネットワーク オフライン / 省電力モード オン」を提示して「このまま期限切れ ¥500」と警告する画面として既に存在する。**権限が無いことが原因で検証できなかった未達成を課金対象にするか**は PRD-03 / PRD-04 の判断だが、PRD-00 §1.1 の性質1（正当な未達成にのみ課金する）に照らせば、**課金しない方向で設計する**のが筋である。

## 5. PWA インストール導線（新規設計）

**現行 UI に該当画面が存在しない。v1 で追加が必要。**

必要な理由は通知の到達性にある。iOS のブラウザでプッシュ通知を受け取るには、ホーム画面に追加された PWA である必要がある。通常のタブで開いているだけでは締切前のリマインダーが届かない。**リマインダーが届かないと未達成が増え、意図しない課金が増える方向に働く**。

### 5.1 決定: 62 の直後に置き、必須にはしない（2026-08-17）

```
62 オンボ作成完了「締切が近づいたら通知します」
        ↓
【新規】PWA インストール案内
        ↓
61 オンボ カード登録の案内
```

**13 ではなく 62 の直後にする理由**

1. **iOS では PWA でないと通知権限をそもそも要求できない。** ホーム画面に追加された Web アプリでのみ Web Push が動作するため、13 の時点で通知権限を求めても空振りする。13 の通知の行は「マイルストーンを作ったあとに設定します」という**予告**にとどめる
2. **13 の時点ではマイルストーンが1件もなく、通知を受け取る理由がない。** 62 は「締切が近づいたら通知します」と約束する画面であり、その直後に「そのためにホーム画面へ追加してください」と続けるのが、動機が最も高い位置になる
3. カード登録（61）より前に置く。61 は金銭の話であり、そこで離脱されると通知の導線ごと失う

**必須にしない理由**: インストールを強制すると、手順を完了できないユーザーがオンボーディングから抜けられなくなる。代わりに、未インストールのアカウントには**ホームに「締切通知が届きません」の常設表示**を出し、再訪のたびに導線を提供する（PRD-06 で扱う）。

### 5.2 画面の要件

iOS Safari は `beforeinstallprompt` を提供しないため、ワンタップでインストールさせることはできない。**「共有 → ホーム画面に追加」の手順を図で説明する画面**が要る。

- iOS Safari / Android Chrome で手順が異なるため、UA に応じて内容を出し分ける
- Android は `beforeinstallprompt` が使えるため、ボタン1つで完了できる
- 「あとで」を必ず置く
- インストール済みで再訪した場合はこの画面を出さない（`display-mode: standalone` で判定）

## 6. カード登録のタイミング（この PRD の主要論点）

### 6.1 UI に矛盾がある

| 画面 | 主張 |
|---|---|
| 36 セットアップ完了 | 「支払い方法は最初の締切前に登録します」＝ 作成より**後**でよい |
| 61 オンボ カード登録の案内 | 「あとで登録」がある ＝ **任意** |
| 56 カード未登録（作成ブロック） | 「未達成のときに課金するカードが未登録です。登録するとマイルストーンを作成できます」＝ カードが無いと**作成できない** |

### 6.2 解決案

**決定（2026-08-17）: オンボーディングの初回1件だけカードなしで作成でき、それ以降は 56 でブロックする。**

- 根拠は 36 の「支払い方法は最初の締切前に登録します」。**UI が明示的に、初回は作成より後に登録すると宣言している**
- 56 のブロックは、これと矛盾しないよう**オンボーディング完了後の通常の作成フローに限定して適用する**。なお 56 の画面本体は 03 と同じ構成だが、38 や 55 も同じ本体を共有しているため、レイアウトからどちらのフローかは判別できない。適用範囲は仕様として決める必要がある
- これにより「最初の1件を作らせる」（§1-2）を優先しつつ、2件目以降では課金の裏付けを確保できる
- 61 の「登録時に請求は発生しません / 課金の前に必ず通知します / いつでも解除できます」という3点の説明は、離脱を抑えるコピーとして既に適切

### 6.3 決めなければならないこと

**初回マイルストーンの締切までにカードが登録されなかった場合どうするか。** 該当する画面が存在しない。

| 案 | 挙動 | 評価 |
|---|---|---|
| A | 締切前にマイルストーンを自動的にオフにする | 課金されない。ユーザーは「何も起きなかった」経験をする。**採用** |
| B | 未達成として記録するが課金しない | 記録と課金が乖離し、実績画面の数値の意味が濁る |
| C | カード登録を促し続け、登録された時点で過去分を課金する | **不可**。同意なき遡及課金 |

**A を採用する**（2026-08-17 決定）。以下が必要になる。

- 締切の一定時間前に「カードが未登録のため、このままでは自動的にオフになります」と通知する（PRD-06）
- ホームに未登録状態の表示を出す（PRD-02）
- オフになった後の再開導線

### 6.4 14 支払い方法登録

- カード番号 / 有効期限 / セキュリティコード / カード名義、「既定の支払い方法にする」、「Stripeで保護されています」の表示
- **カード情報は Stripe のフォーム（Elements 等）でクライアントから直接 Stripe に送り、サーバーはカード番号を受け取らない**。PCI DSS の対象範囲を狭めるための必須構成

### 6.5 Apple Pay / Google Pay で登録した場合、未達成時の自動引き落としはできるか

#### Stripe との関係

Apple Pay / Google Pay は Stripe の代わりになる決済サービスではなく、**カード情報を安全に提示するためのウォレット**である。決済そのものは常に裏側のカードで行われ、それを処理するのが Stripe になる。

```
ユーザー → Apple Pay（端末に登録済みのカードをトークン化して提示）
                ↓
         Stripe（PaymentMethod として保存し、以後の課金を実行）
                ↓
         カード発行会社
```

したがって「Apple Pay で登録する」は「**Apple Pay 経由でカードを Stripe に登録する**」ことであり、Stripe とは別経路の課金が発生するわけではない。App Store の IAP（アプリ内課金）とも別物で、Web には IAP は存在しない。

なお Apple Pay 単体には継続課金の仕組みが無い。定期的・自動的な引き落としは、Stripe に保存された PaymentMethod に対して行う。

#### 自動引き落としの可否

**できる**（Stripe ドキュメントで確認）。条件は2つ。

1. 保存時に `setup_future_usage: 'off_session'`（または SetupIntent）で将来利用を明示しておく
2. 課金時に PaymentIntent へ `off_session: true` を指定する

ウォレットで保存した決済手段は「顧客が同席していない、事業者起点の支払い」にのみ再利用でき、`allow_redisplay` は `limited` になる。SwitchMe のペナルティ課金は**締切後にサーバーのジョブが実行する不在時の課金**なので、この制約にそのまま当てはまる。逆に、ユーザーが画面にいる状態でウォレットの保存済み手段を使い回すことはできず、その場合はウォレットを再提示させる必要がある（v1 に該当する場面はない）。

**v1 に含める**（2026-08-17 決定）。主経路はカード直接登録（14）とし、**Apple Pay / Google Pay は追加の選択肢として同じ画面に置く**。登録の摩擦が最も小さく、61 からの離脱を減らせる。ただし Apple Pay に保存されるのは端末に紐づくトークン（DPAN）であり、端末の変更や再設定で無効化されうる。課金失敗時の再試行（PRD-00 §5.3）が3回で作成停止になるため、**ウォレットのみを登録しているユーザーには、カードの追加登録を促す**（PRD-04 で扱う）。

## 7. 初回マイルストーン作成（60 → 62）

- 60 は 37（作成・簡単）と同じ7種のプリセット + 「自分で作る」+ 「もっと見る」（→ 21 テンプレート選択）
- 「まずは1つだけ選びましょう。あとから変更・追加できます。」で1件に絞らせている。**この方針を維持する**（初回に複数作らせると、初日から複数の課金リスクを負う）
- 60 には「スキップ」がある。スキップした場合は 18 ホーム（空状態）に着地する
- 62 は作成されたマイルストーンの要約（「ジムに行く / 20:00 まで ・ 月水金 ・ ¥1,000」）と「締切が近づいたら通知します」を提示。**通知が実際に届くかは §5 に依存する**ため、PWA 未インストール時にこの文言を出してはならない

### 7.1 18 ホーム（空状態）

- 「まだマイルストーンがありません」+ 「よく使われる習慣」3件（起床確認 / ジムでトレーニング / 就寝準備）+ 「マイルストーンを作成」
- オンボーディングをスキップしたユーザーの受け皿。**ここからの作成には初回免除を与えない**（2026-08-17 決定）。カード未登録なら 56 でブロックし、「カードを登録する」→ 14 → 作成に戻す
- 56 には「あとで」もあるため行き止まりにはならないが、**カードを登録するまで1件も作れない**状態になる。18 の「よく使われる習慣」3件をタップした場合も同様
- 免除をオンボーディング完走者に限定する理由: 初回免除は「33 で課金の仕組みを見て、60 で目標を選び、62 で内容を確認した」という一連の理解の上に成り立つ。スキップしたユーザーはその過程を経ていないため、課金の裏付けを先に取る

## 8. 受け入れ基準

### 8.1 認証・セッション

- [ ] セッションが無効な状態でどの URL にアクセスしても 12 ログインに到達する
- [ ] 同一の Google / Apple アカウントで再ログインしたとき、既存のマイルストーン・支払い方法・履歴に到達できる
- [ ] ログイン画面に「Xで続ける」が存在しない
- [ ] メール + パスワードで登録したアカウントは、メール確認が完了するまでオンボーディングを先に進めない
- [ ] Google / Apple で登録したアカウントには追加のメール確認を求めない

### 8.2 オンボーディング

- [ ] 33 を経由せずに（ディープリンク等で）マイルストーンを作成できる経路が存在しない
- [ ] ステッパーが 1/3 ログイン → 2/3 権限 → 3/3 初回作成 で一貫している
- [ ] 権限を拒否したまま、その権限を必要とする検証方法のマイルストーンを作成しようとすると警告が出る
- [ ] 62 の直後に PWA インストール案内が出る。「あとで」で先へ進める
- [ ] PWA としてインストール済みの状態で再訪したとき、インストール案内が出ない
- [ ] PWA 未インストールのユーザーに「締切が近づいたら通知します」と表示しない

### 8.3 カードと課金の裏付け

- [ ] カード情報がサーバーを経由しない（Stripe に直接送信される）
- [ ] オンボーディングを完走した場合、初回マイルストーンはカード未登録でも作成できる
- [ ] 2件目以降の作成は、カード未登録のとき 56 でブロックされる
- [ ] オンボーディングをスキップしたユーザーは、カードを登録するまで1件も作成できない
- [ ] カード未登録のまま初回マイルストーンの締切を迎えたとき、課金されず、マイルストーンが自動的にオフになる
- [ ] Apple Pay / Google Pay で登録した決済手段が、締切後の不在時課金（`off_session: true`）で実際に引き落とせる
