## 1. この領域が担うこと

未達成が確定してから課金が完了するまでの処理と、その結果をユーザーに見せる記録・統計。加えて、**課金に納得できないユーザーの救済経路**。

PRD-00 §1.1 の性質1（課金は正当な未達成にのみ発生する）が実際に守られているかは、ここでの記録の粒度と救済の実効性によって検証される。

---

## 2. 課金のライフサイクル

### 2.1 状態

48 課金明細に「状態: 確定」の表示があることから、課金は状態を持つ。

| 状態 | 意味 | 遷移元 |
|---|---|---|
| 保留 | 未達成が確定し、課金の実行待ち | 締切到達 |
| 確定 | 課金に成功した | 保留 |
| 失敗 | 課金に失敗し、再試行を待っている | 保留 / 失敗 |
| 中止 | 3回失敗して打ち切った | 失敗 |
| 返金済み | 確定後に返金した | 確定 |

**「保留」を独立した状態にする理由**: 締切到達と決済 API の応答は同時ではない。締切の瞬間に大量のインスタンスが同時に確定するため、決済はキューで順次処理される。この間、ユーザーの画面には「未達成」が見えているが課金は完了していない。この期間を状態として持たないと、二重課金や取りこぼしを検知できない。

### 2.2 冪等性

同じインスタンスに対して課金が二重に実行されないことを保証する。**インスタンスID を決済の冪等キーとして使う**。64 返金についてが「二重に課金された場合」を例外的な返金対象として挙げており、起こりうる事故として想定されている。

### 2.3 課金の実行主体

サーバーのジョブ。クライアントからは叩かない（PRD-00 §5.1）。アプリを開かなければ回避できてしまうため。

## 3. 課金の失敗（20 / 50）

### 3.1 リトライ

20 の表示より確定している仕様。

- 自動再試行は**最大3回**
- 間隔は日単位（「次回の自動再試行 8月10日 09:00」）
- 現在の回数を表示する（「再試行回数 2回 / 最大3回」）
- 「あと1回失敗すると作成が停止されます」と事前に警告する
- ユーザー操作: 「支払い方法を更新」「今すぐ再試行」

### 3.2 作成の停止

**3回失敗すると新しいマイルストーンを作成できなくなる。** 50（カード期限切れ）も同じ制限を課す（「更新するまで新しいマイルストーンは作成できません」）。

### 3.2.1 既存マイルストーンの扱い（2026-08-17 決定）

**全て休止する。カードを登録・更新したら復帰できるが、自動では復帰しない。**

| 段階 | 挙動 |
|---|---|
| 3回失敗 / カード期限切れ | 実行中のマイルストーンを**全て休止**する。検証も課金も止まる |
| カードを登録・更新 | 休止は解除されない。**ユーザーが明示的に再開する** |
| 再開 | 休止中だったマイルストーンを個別またはまとめて実行中に戻す（52 / 73 の既存操作を使う） |

**自動復帰させない理由**: カードを更新した瞬間に、止まっていた複数のマイルストーンが一斉に有効になると、ユーザーが把握しないまま当日の締切と課金が復活する。再開はユーザーが意識して行う操作にする。

支払える状態にないユーザーに債務を積み上げないことが目的であり、PRD-00 §7.2 #4（無通信時の自動停止）と同じ構造の出口になる。

**必要な画面**: 休止された状態と、その理由（課金失敗 / カード期限切れ）、再開の導線。20 / 50 に追加するか新規に作るかは §10。

### 3.3 未払いの扱い

3回失敗して中止した課金をどう扱うかも未定義（§9 #2）。債権として残して後日請求するのか、放棄するのか。**放棄を推奨する** — 少額の債権回収はコストに見合わず、督促は体験を著しく損なう。ただし会計処理と規約への記載が必要。

## 4. 支払い方法（14 / 23 / 50）

- 23 は**複数カードの登録**と「既定」の指定に対応している（VISA ····4242 が既定、Mastercard ····8891 が2枚目）
- 既定のカードで失敗した場合、2枚目に自動でフォールバックするかは未定義（§9 #3）。**フォールバックする**方が課金の成功率は上がるが、ユーザーが意図しないカードから引き落とされる
- 50 はカード期限切れを**事前に検知**して警告する。有効期限をサーバー側で保持し、期限の一定期間前に通知する（PRD-06）
- Apple Pay / Google Pay も同じ一覧に並ぶ（PRD-01 §6.5）。ウォレットのみの登録は端末変更で無効化されうるため、**カードの追加登録を促す**（PRD-01 §10 #4 の積み残し。23 に案内行を追加する）

## 5. 記録の表示

### 5.1 04 実績

| 要素 | 内容 |
|---|---|
| 達成率 | 82% / 先月比 +6pt |
| 合計ペナルティ | ¥2,400 / 未達成 4件 |
| 曜日別 | 直近4週間のバー |
| 検証方法別 | 位置 94% / 写真 78% / コード 61% |
| ペナルティ履歴 | 直近数件 + 「すべて見る」 |

**検証方法別の達成率は運用上の重要指標**である。コードが 61% と低いのは、読み取りの失敗率か、そもそも達成しにくい習慣に使われているかのどちらか。この数値が判定の閾値調整（PRD-03 §4.2）の入力になる。

### 5.2 指標の定義

UI に数値が出ている以上、定義を確定させる必要がある。

| 指標 | 定義 |
|---|---|
| 達成率 | 達成インスタンス ÷ 決着したインスタンス。**オフ期間中のインスタンスは分母に含めない**（検証も課金も行われないため） |
| 合計ペナルティ | 当月に**確定**した課金の合計。保留・失敗中は含めない |
| 連続（ストリーク） | 46a2 は「起床確認 / 5日連続」= **定義ごと**。49 の「12日 連続」は**アカウント全体**と読める。**2種類あることを明示する**（§9 #4） |
| 曜日別 | 直近4週間の、その曜日の達成率 |
| 検証方法別 | 検証方法ごとの達成率（全期間か期間限定かは未定義） |

### 5.3 「今月の課金リスク ¥2,400 / ¥8,000」（46a2 / 46b）

ホームに出るこの表示の意味を確定させる。

- **¥2,400** = 当月に確定した課金の合計
- **¥8,000** = 当月に設定されているマイルストーンの罰金額の合計（すべて未達成だった場合の最大額）

**これは上限ではなく予測である。上限は設けない**（2026-08-17 決定）。

一定額に達したら課金を止める仕組みは作らない。ユーザーが自分で設定した金額とマイルストーンの数がそのまま上限であり、それを超える課金は発生しない。¥8,000 の表示は「今月これだけのリスクを負っている」ことを可視化するためのものとして維持する。

なお1件あたりの上限は ¥50,000（55 カスタム罰金）で既に存在する。

### 5.4 10 課金・支払い履歴

- 月次のペナルティ合計と前月比
- 月別のバー（3月〜8月）
- 既定のカード表示と「変更」
- **達成分も含む時系列リスト**（「就寝準備 / 8月8日 / 達成」「シャワー確認 / 8月8日 / -¥300」）

課金の履歴に達成が混ざっているのは、「払わずに済んだ日」を見せる意図と読める。この構成を維持する。

### 5.5 48 課金明細

| 項目 | 例 |
|---|---|
| 金額 | ¥500 |
| マイルストーン | 朝の準備 |
| 日時 | 2026/08/09 07:30 |
| 判定 | 不一致 |
| 検証 | 写真 |
| 支払い | VISA •••• 4242 |
| 状態 | 確定 |
| 証跡 | （画像 / 位置 / 一致結果） |

**証跡の表示は検証方法によって変わる**（PRD-03 §7.3）。

| 検証方法 | 証跡 | 保持 |
|---|---|---|
| 写真 | 提出した画像 | 30日 |
| 出発 / 到着 | 位置と目標地点の関係 | 90日 |
| コード | 一致 / 不一致の記録のみ | — |

保持期間を過ぎた場合、およびユーザーが「検証データを削除」した場合の表示が必要（PRD-03 §11 #4）。

## 6. 返金と異議申し立て

### 6.1 64 が定めているポリシー

現行 UI が既に明文化している。**これを正とする。**

| 区分 | 内容 |
|---|---|
| 原則 | 確定した課金は返金できない。未達成の判定は自分で設定した条件にもとづいて自動で行われるため |
| 例外的に返金する | アプリの不具合でセンサーが正しく動かなかった場合、二重に課金された場合など、**当社に原因があるとき** |
| 返金しない | 判定に納得できない、うっかり忘れた、体調が悪かった |
| 導線 | 課金明細のスクリーンショットを添えて問い合わせる |

「返金しない場合」に**判定に納得できない**が含まれている点が重要である。これは PRD-03 §4.2（判定にバイアスをかけず、閾値は1つ）と整合する。判定の妥当性そのものを争う経路は用意せず、**こちら側の瑕疵に限って返金する**という立て付けになっている。

### 6.2 独立した異議申し立て画面は作らない

65 問い合わせが「種類=課金のこと」+「関連するマイルストーン」で窓口を兼ねている。異議申し立て専用の画面は作らない。

**理由**: 64 が返金の範囲を「当社に原因があるとき」に限定している以上、必要なのは再審査の申請フォームではなく**不具合の報告経路**である。65 の構成（種類・関連マイルストーン・内容・スクリーンショット添付）がその要件を満たしている。

### 6.3 48 から 64 / 65 への導線が無い

課金明細を見て納得できなかったユーザーが、その場から問い合わせに進めない。**48 に「この課金について問い合わせる」を追加する**（§10 #1）。65 の「関連するマイルストーン」に該当の課金を自動で紐づけられるため、往復も減る。

### 6.4 運用の前提

65 は「通常2営業日以内に登録メールアドレスへ返信します」と約束している。**返信できる体制がないまま v1 を出すことはできない**（PRD-00 §10 #5）。

- 受信箱の運用担当を決める
- 返信のテンプレートを用意する（不具合が確認できた場合 / 確認できなかった場合）
- 返金の実行手順（Stripe の返金 API と、48 の状態を「返金済み」に更新する処理）

## 7. 法務・表示

v1 は Web で直接課金するため、以下が**ローンチの前提条件**になる。

| 項目 | 内容 |
|---|---|
| 特定商取引法に基づく表示 | 事業者名・所在地・連絡先・支払い時期・支払い方法・返品/返金の条件。29 利用規約・課金ポリシーに含めるか独立させるか要判断 |
| 消費税 | 罰金は役務の対価か、それとも違約金か。**課税区分が変わる**ため確認が必要（§9 #6） |
| 返金ポリシー | 64 の内容を規約にも反映する |
| 資金決済法 | 該当しない想定（前払式支払手段ではない）だが確認する |

**「ペナルティ」という商品性そのものが確認を要する。** ユーザーが自分に課す違約金を事業者が徴収する構造であり、一般的な物販・役務提供とは異なる。**法務確認を最優先事項とする。**

## 8. 受け入れ基準

### 8.1 課金

- [ ] 同一インスタンスに対する課金が二重に実行されない
- [ ] 締切到達から課金完了までの間、課金が「保留」状態として識別できる
- [ ] 課金失敗時、最大3回まで自動で再試行される
- [ ] 3回失敗した後、新しいマイルストーンを作成できない
- [ ] カード期限切れの状態で新しいマイルストーンを作成できない
- [ ] オフ期間中のインスタンスに課金が発生しない
- [ ] カード未登録のオンボーディング初回マイルストーンに課金が発生しない（PRD-01 §6.3）

### 8.2 記録

- [ ] 達成率の分母にオフ期間中のインスタンスが含まれない
- [ ] 合計ペナルティに保留中・失敗中の課金が含まれない
- [ ] 48 の証跡が、検証方法に応じた内容で表示される
- [ ] 保持期間を過ぎた証跡について、その旨が表示される
- [ ] 10 の履歴に達成分も表示される

### 8.3 救済

- [ ] 48 から問い合わせに進める
- [ ] 問い合わせに課金 ID・マイルストーン ID・アプリバージョン・OS が自動で紐づく
- [ ] 返金を実行すると 48 の状態が「返金済み」になる
