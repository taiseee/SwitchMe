# PRD-06 通知・評価依頼

作成日: 2026-08-17
ステータス: ドラフト（レビュー待ち）
前提: [PRD-00](./00-product-definition.md) 〜 [PRD-05](./05-settings-support.md)

対象画面: 24 設定/通知 / 77 ロック画面（通知）/ 78 通知パターン一覧 / 84 評価依頼（初回達成後）/ 85 評価依頼（1週間後以降の達成）

一次情報: `ui.pen` NOTE「評価依頼モーダルの表示条件」

## 1. この領域が担うこと

**v1 では通知がプロダクトの成立条件になる。**

PRD-00 §2.1 の通り、v1 に自動達成は無い。検証は必ずユーザーが締切前にアプリを開いて実行する。**開かなければ課金される。** つまり通知は「あると便利な機能」ではなく、**課金の妥当性（PRD-00 §1.1 の性質1）を支える仕組み**である。

78 のヘッダーがこれを明示している。

> 送信条件ごとの文面と見た目。自動検証は行わないため、通知はすべてユーザーの行動を促すか、確定した結果を伝えるかのどちらか。

加えて、61 オンボ カード登録の案内が画面上で **「課金の前に必ず通知します」** と約束している。これは規約と同様に**守らなければならない約束**であり、§5 の中心的な論点になる。

## 2. v1（Web PWA）の配信基盤

### 2.1 プラットフォーム制約

| 項目 | v1 での扱い |
|---|---|
| 配信方式 | **Web Push（サーバー送信）のみ** |
| 端末側でのスケジュール | **できない**。Notification Triggers API は未実装。締切30分前などの時刻指定は**すべてサーバー側のスケジューラで送る** |
| iOS | **ホーム画面に追加した PWA でのみ動作する**。通常の Safari タブでは通知権限を要求すらできない |
| Android Chrome | ブラウザのタブでも動作する。インストールは必須ではない |
| 権限要求 | ユーザー操作（タップ）を起点とする必要がある。自動では出せない |
| 購読の失効 | プッシュ購読は無効化されうる（送信時に 410 Gone が返る）。**失効を検知して再購読を促す経路が要る** |

### 2.2 サーバー側スケジューラが必要になる

端末に予約できない以上、次のすべてをサーバーが時刻管理する。

- マイルストーンごとの締切時刻（ユーザーのタイムゾーン込み）
- 事前リマインドのオフセット（§4.2）
- 締切到達時の未達成確定と、それに続く課金・通知
- オフ期間の終了予告（78 #11）
- 未作成リマインド（78 #12）

**日付の境界は「一日の開始時刻」（既定 06:00、PRD-05 §3.2）に従う。** 締切に 06:00 より前の時刻が設定されている場合、それは翌日を指す。事前リマインドの送信時刻もこの解釈に従って計算する。

### 2.3 到達率は前提にできない

以下のいずれかでプッシュは届かない。

| 状態 | 発生条件 |
|---|---|
| iOS でホーム画面未追加 | PWA インストールを必須にしていない（PRD-01 §5.1） |
| 通知権限が未許可・拒否 | 権限を任意にしている |
| 購読が失効 | 端末側の都合。検知は送信時 |
| 端末がオフライン | 一時的。復帰時に配信されるとは限らない |

**PRD-01 §5.1 で PWA インストールを必須にしないと決めている以上、「プッシュが届かないユーザー」は無視できない規模で存在する。** §5 でその扱いを決める。

## 3. 通知カタログ（78）

### 3.1 描画されている7種

78 に設計されているのは以下。番号は 78 の表示どおり。

| # | 名称 | 送信条件 | タイトル | 本文 | タップ先 |
|---|---|---|---|---|---|
| 01 | 事前リマインド | 締切30分前 | 作業開始確認 | あと30分で締切です。デスクを撮影して検証しましょう。 | 02 / 05 / 06 検証画面 |
| 02 | 直前警告 | 締切5分前 | まもなく締切 | あと5分で「作業開始確認」が未達成になります（¥800） | 02 / 05 / 06 検証画面 |
| 05 | 検証失敗・課金確定 | 期限超過／判定NG | 朝の準備完了 未達成 | ペナルティとして ¥300 が課金されました。 | 46b 検証結果（未達成） |
| 06 | 決済失敗 | カード決済エラー | 決済に失敗しました | カードを確認してください。24時間後に再試行します。 | 20 課金処理失敗・リトライ |
| 07 | カード期限切れ間近 | 失効30日前 | カードの有効期限 | 登録中のカードが今月末で失効します | 23 設定/支払い方法 |
| 11 | 休止終了の予告 | オフ期間の前日 | 明日から再開します | 休止中の3件のマイルストーンが再開します | 01 ホーム |
| 12 | 未作成リマインド | 登録後3日 未作成 | まだマイルストーンがありません | テンプレートから30秒で作成できます | 37 作成（アクション選択） |

**番号は 03 / 04 / 08 / 09 / 10 が欠番**である。78 のヘッダーが「自動検証は行わないため」と断っていることから、欠番は自動検証に紐づく通知（自動達成の検知、バックグラウンド判定の結果など）と考えられる。**欠けている番号の通知を推測して補わない。** 必要になった時点で 78 に追加する。

### 3.2 v1 で追加が必要な通知

現行の7種では、既に確定している要件を満たせない。以下を追加する。

| # | 名称 | 送信条件 | 根拠 |
|---|---|---|---|
| 13 | カード未登録の警告 | オンボーディング初回マイルストーンの締切前 | PRD-01 §6.3。締切前に自動オフにする前の予告 |
| 14 | 全マイルストーン休止の通知 | 課金3回失敗またはカード期限切れ | PRD-04 §3.2.1。復帰はユーザー操作なので、休止したことを知らせないと止まったままになる |
| 15 | 再審査の結論 | 再審査中の課金に結論が出たとき | PRD-05 §2.5。誤検知と認めた／認めなかったの通知 |
| 16 | 返金の完了 | 返金処理が完了したとき | PRD-04 §6.4 |

いずれも金銭に関わるため、§5 の配信保証の対象になる。

### 3.3 タップ先（ディープリンク）

78 は各通知のタップ先を明示している。v1 では**通知タップから該当画面へ直接遷移する**こと。ホームに着地させて探させない。

- 01 / 02 → その場で検証を開始できる画面（検証方法により 02 / 05 / 06 に分岐）
- 05 → 46b 検証結果（未達成）
- 06 → 20 課金処理失敗・リトライ
- 07 → 23 設定/支払い方法

**未ログイン状態で通知をタップした場合**、ログイン後に元の遷移先へ復帰させる。ITP でセッションが切れている可能性がある（PRD-00 §2.2）ため、この復帰は例外ではなく通常経路として実装する。

## 4. 通知設定（24）

### 4.1 描画されている内容

| セクション | 項目 | 既定 |
|---|---|---|
| 通知の種類 | 検証結果 | オン |
| | 課金確定 | オン |
| | 自動検証の結果 | オン |
| リマインダー | リマインダー | オン |
| | 事前リマインド | 値の表示は「15分前・1時間前」 |
| その他 | サウンド | **オフ** |

事前リマインドの行に出ている「15分前・1時間前」は、**現在選ばれている値の表示**である。選択肢そのものは 24 に描画されていない（遷移先のシートが未設計）。複数の値が同時に選ばれている状態を示している点だけが読み取れる。

### 4.2 「事前リマインド 15分前・1時間前」と 78 の「30分前」が食い違う

24 は事前リマインドの値として「15分前・1時間前」を表示し、78 のパターン 01 は「締切30分前」、パターン 02 は「締切5分前」としている。

**決定**: 役割の違う2つとして分ける。

| 通知 | 性質 | 設定 |
|---|---|---|
| **事前リマインド**（78 #01） | 行動を促す。複数回送ってよい | **ユーザーが選ぶ**。15分前 / 30分前 / 1時間前 / 2時間前 から複数選択可。既定は 30分前 |
| **直前警告**（78 #02） | 課金の直前予告。61 の約束に対応する | **固定で締切5分前**。ユーザーは変更できない（§4.4） |

24 の「事前リマインド」行はこの複数選択のシートへ遷移する。78 のパターン 01 が 30分前なのは既定値の例示として整合する。

**選択肢の4件（15分前 / 30分前 / 1時間前 / 2時間前）は本 PRD での提案であり、`ui.pen` には存在しない。** 24 が示しているのは「複数選択である」ことだけで、シート自体が未設計である（§11 #3）。

### 4.3 「自動検証の結果」は v1 では出さない

自動検証（バックグラウンドでの位置判定による自動達成）は **v1 では提供せず、Phase 2 でも最後に着手する**（PRD-00 §2.3）。存在しない機能のトグルを設定画面に置かない。

**24 からこの行を削除する**（§11 #1）。Phase 2 で自動検証を実装するときに戻す。

### 4.4 課金に関わる通知はオフにできない

24 の「課金確定」はトグルになっている。**これをオフにできる設計は採らない。**

理由は3つある。

1. **61 が「課金の前に必ず通知します」と約束している。** ユーザーがトグルを切れる状態では、この約束を守れない
2. 金銭の請求が発生したことを知らせないのは、消費者保護の観点で問題がある
3. 通知を切ったことを忘れたユーザーが、身に覚えのない請求として問い合わせる（PRD-05 §8.1「なぜ課金されたのか」が最も引かれる項目になる）

**決定**: 次を「切れない通知」とし、24 のトグルから外す。

| 通知 | 理由 |
|---|---|
| 02 直前警告 | 61 の約束 |
| 05 検証失敗・課金確定 | 請求の告知 |
| 06 決済失敗 | 対応しないと全マイルストーンが休止する（PRD-04 §3.2.1） |
| 07 カード期限切れ間近 | 同上 |
| 13 カード未登録の警告 | 自動オフの予告 |
| 14 全マイルストーン休止 | 休止したことに気づけない |
| 15 再審査の結論 / 16 返金の完了 | 申し立てへの回答 |

24 に残すトグルは「検証結果（達成時）」「リマインダー（事前リマインド）」「サウンド」と、追加する「休止終了の予告（78 #11）」「未作成リマインド（78 #12）」になる。**「切れない通知があること」を 24 に明記する**（§11 #2）。

### 4.5 サウンドが既定オフである意味

24 のサウンドは既定オフで描画されている。**このまま採用する。** 締切前の催促を音で鳴らすと、朝の締切（起床系のプリセット既定は 08:00）では目覚まし時計として使われ、プロダクトの位置づけが変わる。音はユーザーが明示的にオンにしたときだけ鳴らす。

## 5. プッシュが届かない場合（配信保証）

### 5.1 61 の約束は Web Push だけでは守れない

61 の **「課金の前に必ず通知します」** は、§2.3 の理由でプッシュ単独では成立しない。**約束を維持するなら経路を増やす。文言を弱めるなら 61 を書き換える。** どちらかを選ぶ必要がある。

**決定: 経路を増やす。** 61 の文言は維持し、金銭に関わる通知は**メールでも送る**。

| 通知 | プッシュ | メール |
|---|---|---|
| 01 事前リマインド | ○ | — |
| 02 直前警告 | ○ | **○** |
| 05 検証失敗・課金確定 | ○ | **○** |
| 06 決済失敗 | ○ | **○** |
| 07 カード期限切れ間近 | ○ | **○** |
| 11 休止終了の予告 | ○ | — |
| 12 未作成リマインド | ○ | — |
| 13 カード未登録の警告 | ○ | **○** |
| 14 全マイルストーン休止 | ○ | **○** |
| 15 再審査の結論 / 16 返金の完了 | ○ | **○** |

メールは v1 で必ずアドレスを持っている（PRD-01 §2.2 でログイン必須、ソーシャルログインでもアドレスを取得する）。

**61 は「あとで登録」でスキップできる**（PRD-01 §6.2）。スキップしたユーザーはこの約束を目にしないが、**約束はプロダクトの表示であってユーザーごとの契約ではない**ため、対象を絞らず全ユーザーに適用する。なお 29 課金ポリシーにはこの約束が書かれていない。**規約側にも同じ内容を書くかは要判断**（§10 #7）。

**02 直前警告のメールについては要判断**（§10 #1）。毎日複数件のマイルストーンがあるユーザーには、締切ごとにメールが届くことになる。1日1通にまとめる案（その日の残り全件を1通で送る）を検討する。

### 5.2 メールからカード停止・退会に到達できる経路

PRD-01 §2.2 が既に指摘している通り、**ITP でセッションが切れたユーザーは、課金だけが動き続ける状態になりうる**。

**すべての課金関連メールに、次の導線を含める。**

- 課金明細（48）へのリンク
- **支払い方法の停止**へのリンク
- **退会**（74）へのリンク

これらはログインを要求してよいが、**メールアドレス宛のワンタイムリンクでログインできる**ようにする。パスワードを覚えていないユーザーがカードを止められない状態を作らない。

**この導線は現行 UI に存在しない。新規設計が必要**（§11 #4 / #5。PRD-01 §3.2 の積み残しをここで引き取る）。

### 5.3 プッシュ購読の失効

送信時に 410 Gone / 404 が返ったら、その購読を無効として記録する。次回アプリを開いたときに再購読を促す。**再購読を促さずに黙って通知が止まる状態を作らない。**

### 5.4 PWA 未インストールのユーザー

PRD-01 §5.1 でインストールを必須にしていない。iOS の未インストールユーザーにはプッシュが一切届かない。

- **62 オンボ作成完了の「締切が近づいたら通知します」を、未インストールのユーザーには表示しない**
- 代わりに「メールでお知らせします」と表示する
- 未インストールのまま初回の未達成が発生したユーザーには、課金確定メールにインストール導線を含める

## 6. 評価依頼（84 / 85）

### 6.1 描画されている内容

84 と 85 はホーム（01）の上に重なるモーダルで、見出し以外は同一である。

| 要素 | 84 | 85 |
|---|---|---|
| アイコン | 🎉 | 🎉 |
| 見出し | はじめての達成 | 9日連続で達成中 |
| 本文 | SwitchMe はどうですか？ | 同左 |
| 評価 | 星5つ | 同左 |
| 主ボタン | App Store で評価する（外部リンク） | 同左 |
| 副ボタン | あとで | 同左 |

### 6.2 トリガ

**表示は2回だけである。**

| 回 | 条件 | 画面 |
|---|---|---|
| 1回目 | **初めてマイルストーンを達成した直後** | 84 |
| 2回目 | **利用開始から1週間以上たったあとの達成の直後**（1回目とは別の達成） | 85 |

どちらも**それぞれ1回きり**で、以後は出さない。

**「利用開始」はアカウント登録日とする。** 初回達成が登録から1週間以上あとに起きた場合、84 と 85 の条件が同時に成立するが、**同じ達成で2つ出さない**。85 はその次の達成で出す。

挙動:

- **検証結果（達成）を閉じてホームに戻った直後**に重ねる（PRD-03 §8.3 と一致）
- 検証中・検証失敗の直後には出さない
- 星をタップした時点で閉じる
- 「あとで」は評価せずに閉じるだけ。84 で押しても、次に出るのは 85 のタイミングである

### 6.3 保持する状態

| 名前 | 内容 |
|---|---|
| `account_started_at` | アカウント登録日。2回目の条件の起点 |
| `rating_prompt_84_shown_at` | 84 を表示した時刻。未設定なら初回達成で 84 を出す |
| `rating_prompt_85_shown_at` | 85 を表示した時刻。未設定かつ 84 表示済みかつ登録から7日以上経過なら、次の達成で 85 を出す |
| `rating_stars` | 星の評価値（§6.4） |

**除外条件は設けない。** 直近の課金の有無、未クローズの問い合わせ、締切時間帯などによる抑制は行わない。回数を2回に限ること自体が抑制になっている（§6.5）。

### 6.4 v1 に App Store は存在しない

84 / 85 の主ボタンは「App Store で評価する」で、NOTE が記す機構（StoreKit `requestReview`、`write-review` URL、`UIActivityViewController`）はすべてネイティブのものである。**v1 は Web PWA であり、App Store のページが無い。**

PRD-00 §8 は既に「v1 の 84 / 85 はアプリ内フィードバックとして扱う」と決めている。これを具体化する。

**決定（v1）**:

| 操作 | 挙動 |
|---|---|
| 星をタップ | 評価値を記録してモーダルを閉じる。これ自体がアプリ内フィードバック |
| 星が 1〜3 | 閉じたあとに「よければ理由を教えてください」を1行で出し、65 問い合わせ（種類 = その他、プリフィルあり）への導線にする |
| 星が 4〜5 | 閉じるだけ。追加の要求はしない |
| 「App Store で評価する」ボタン | **v1 では出さない**。代わりに「あとで」のみを残す |
| 「あとで」 | 評価せずに閉じる。次に出るのは 85 のタイミング（§6.2） |

11 設定の「App Store で評価する」も同じ理由で v1 では出さない（PRD-05 §8.3 で決定済み）。「アプリを共有する」は Web Share API で成立するため残す。

**Phase 2（ネイティブ）での注意**: Apple のガイドラインは、評価の高低でストアへの誘導を出し分けること（レビューゲーティング）を認めていない。上記の「星1〜3 のときだけ問い合わせへ誘導する」構造は、**ストアへの導線が存在しない v1 でのみ成立する**。ネイティブ版では StoreKit の `requestReview` に置き換え、星による分岐は行わない。

### 6.5 出す回数を2回に限る理由

ペナルティを課すプロダクトで「SwitchMe はどうですか？」を出せるタイミングは限られる。**達成直後という起点は、直前に金を払った体験と隣り合っている。**

回数を絞ることがそのまま抑制になる。条件で細かく弾くのではなく、**生涯で2回しか出さない**という単純な規則にした。v1 は §6.4 の通りストアへ誘導しないため、実害はさらに小さい。

## 7. 77 ロック画面（通知）の位置づけ

77 は通知の見た目を確認するためのモックであり、実装対象の画面ではない。3件（直前警告 / 事前リマインド / 未達成確定）が積まれた状態を示している。

読み取れる要件:

- **アイコンは SwitchMe の稲妻マーク**（黄色）。通知の種類でアイコンを変えない
- タイトルは**マイルストーン名**または**状態**（「まもなく締切」「朝の準備完了 未達成」）
- 本文に**金額を明示する**（「¥800」「¥300」）
- 時刻を右上に表示（OS 標準）

**金額を通知に載せることは維持する。** 締切前に「いくら失うか」が見えていることが、行動を促す唯一の材料である。

## 8. 受け入れ基準

- [ ] 事前リマインドが 15分前 / 30分前 / 1時間前 / 2時間前 から複数選択できる

- [ ] 評価依頼が生涯で2回を超えて表示されない
- [ ] v1 で「App Store で評価する」が表示されない
- [ ] 検証中・検証失敗の直後に評価依頼が表示されない
