## 2. マイルストーンのモデル

### 2.1 定義と実体を分ける

UI を読むと、2つの異なる概念が同じ「マイルストーン」という言葉で扱われている。

| 概念 | 実体 | 画面 |
|---|---|---|
| **定義** | 「平日 08:00 までに起床する / ¥500」というルール | 52 一覧、40 編集 |
| **インスタンス** | 「8月17日（月）08:00 の起床確認」という1回分 | 01 ホーム、01d 完了リスト |

52 の各行は定義、01 の各行は今日のインスタンス。**課金はインスタンス単位**で発生し（48 課金明細が「2026/08/09 07:30」と日時を持つ）、削除や編集は定義に対する操作になる。この区別が §7 の締切ガードの土台になる。

**訂正（2026-08-17 UI 実描画監査）**: 当初「52 の一部の行に **完了** バッジが付いているのは誤り」と記述し `ui.pen` 側を「休止中」に修正したが、**この Status Chip ノード群は `enabled: false` であり、そもそも画面に描画されていなかった**。書き出した PNG で確認済み。したがって 52 に「完了」バッジが表示されたことはなく、修正は表示上は無変更である。詳細は PRD-00 §0.6。

**52 の行に描画されている状態表示はトグルスイッチのみ**である。実行中／休止中のテキストチップは描画されない設計バリアント（死にノード）として `ui.pen` に残っている。定義が取る状態は §2.3 の2つだけである。

### 3.1 撮影対象の候補（75）

| カテゴリ | 対象 |
|---|---|
| 部屋・寝室 | ベッド / デスク / 部屋の照明 |
| 水まわり | 洗面台 / シャワー / 歯ブラシ |
| 外出・運動 | 玄関 / ジム機器 / シューズ |
| 食事 | 食事 / お弁当 / プロテイン |

**描画されているのは上の12種**（2026-08-17 PNG で確認）。**正は [PRD-03 §3.1](./03-verification.md) の撮影対象カタログ**（v1 で提供する物体型24種、状態型・数値型7種は Phase 2）であり、75 はそこへ拡張する。

58b は「選んだ写真が検証画面で見本として表示されます」と説明する。**撮影対象は判定の基準であると同時に、検証画面（02 / 43）の見本表示にも使われる**。

38f（就寝準備）は「何を撮影する？ ベッド / 寝室 / 洗面台 / その他」を作成画面にインラインで持つ。75 の全リストとは粒度が違う（「寝室」は 75 に存在しない）。**75 に統一する**（[PRD-03 §3.1](./03-verification.md) で決定。「その他」は設けない）。

### 3.2 場所の選択（39 / 58）

- 地図上で候補を提示し、カテゴリで絞る: ジム / 自宅 / カフェ / コワーキング / 学校
- 選択したピンを中心に半径円を表示
- 「ここにする」で確定。検索バーで任意地点も指定可
- 距離表示あり（「エニタイムフィットネス 渋谷 / 420m」）

**v1 での注意**: 位置情報はフォアグラウンド取得のみ（PRD-00 §2.1）。「到着」の判定はユーザーが現地でアプリを開いて「現在地で検証」を押した時点の座標で行う。滞在時間は扱わない。

### 3.3 コードの登録（76）

- 「登録するコードを読み取ってください / 次回からこのコードと一致するか判定します」
- 読み取った内容を表示（「ザバス ホエイプロテイン / JAN 4902777 310527」）
- 「読み直す」「このコードを登録」

商品名の表示は、JAN から商品マスタを引く必要がある。**外部データベースへの依存**が発生するため、v1 では商品名を出さずコード値のみ表示する選択肢もある（§10 #2）。

## 4. 作成フロー

### 4.1 UI に 3 系統が存在する

| 系統 | 経路 | 特徴 |
|---|---|---|
| A. 簡単 | 37 アクション選択 → 38x | 全項目が埋まった**1画面**で調整して作成 |
| B. ウィザード | 63(1/4) → 57(2/4) → 58/58b/58c(3/4) → 59(4/4) | 4ステップ。59 の次は「内容を確認」 |
| C. 詳細 | 03 | 最初から全項目の1画面 |

**B の「内容を確認」の遷移先が画面として存在しない。**

### 4.2 決定: A と B の両方を残し、入口で使い分ける（2026-08-17）

```
60 オンボ目標選択  ┐
21 テンプレート     ├→ (B) 63 → 57 → 58/58b/58c → 59 →「内容を確認」→ 38x → 作成
37 プリセット      ┘

37「自分で作る」  ──→ (A) 03 詳細（1画面）───────────────────→ 作成
```

| 入口 | フロー |
|---|---|
| 60 オンボ 目標選択 | **B**（4ステップ） |
| 21 テンプレート選択 | **B** |
| 37 のプリセット7種（起床する / ジムに行く 等） | **B** |
| 37「自分で作る」 | **A**（03 詳細の1画面） |

**38a〜38f の位置づけ**: B の最終ステップ「内容を確認」の着地点。全項目が埋まった状態を1画面で提示し、そこから作成する。詳細画面（03）と同じ本体を共有しているのはこのためである。

**この構造にする理由**: 作成の最終画面では「**何を・いつまでに・いくら**」が同時に見えている状態で作成ボタンを押させる（PRD-00 §3.3）。金額を単独のステップに隔離したまま確定させると、コミットメント全体を把握しないまま契約が成立してしまう。これは認知負荷の話ではなく**契約の可視性の要件**であり、他の理由で覆さない。B は金額を 4/4 に隔離しているため、38x を確認画面として挟むことで要件を満たす。

自分で作る場合（A）は、ユーザーが全項目を意識的に設定しているため、確認ステップを重ねる必要がない。

### 4.3 21 テンプレート選択

- カテゴリ: すべて / 朝の習慣 / 生産性 / 健康管理 / 夜
- テンプレートは時刻と金額を含む（「起床確認 / 平日 8:00 · ¥500」）
- 検索あり
- 37 の「もっと見る」から到達

37 のプリセット（7種のアクション）と 21 のテンプレート（時刻・金額込み）は**別のもの**である。37 は「何をするか」、21 は「設定済みの完成品」。

### 4.4 開始日と締切日は別の概念

| 画面 | 対象 | 文言 |
|---|---|---|
| 66 / 67 | 締切日 | 「締切日を選ぶ / 今日より前の日付は選べません」 |
| 68 / 69 | 開始日 | 「開始日を選ぶ / この日からマイルストーンが始まります」 |
| 63 | 開始日 | 「いつから始める？ / 繰り返しをオンにすると毎回この習慣が作られます」 |

**繰り返しありなら開始日、繰り返しなしなら締切日**、という使い分けと読める。両者が同じ「今日 / 明日 / 選択」の UI を共有しているため、実装時に取り違えやすい。**繰り返しの有無で日付欄のラベルを切り替える**こと。

## 7. 締切ガード（v1 ブロッカーの解決）

### 7.1 問題

現状、締切直前の操作に対するガードは **71（オフ期間）にしか存在しない**。8:00 締切のマイルストーンを 7:59 にスワイプ削除すれば課金を回避できる。削除・金額引き下げ・締切時刻の変更・検証方法の変更、いずれも無防備である。

### 7.2 決定案: 「今日のインスタンスは締切6時間前で凍結する」

**原則**: 締切の6時間前を過ぎたら、**今日のインスタンスに対する変更を一切受け付けない**。すべての変更は**翌日以降のインスタンスにのみ適用される**。

この原則で、既存の 71 のルール（当日オフ不可）を含むすべての操作を統一的に説明できる。

| 操作 | 6時間前より前 | 6時間前を過ぎた後 |
|---|---|---|
| 削除 | 定義ごと削除。今日の分も消える | **今日の分は残る**（課金対象のまま）。明日以降が作られなくなる |
| オフにする | 今日から適用 | **明日から適用**（71 の既存挙動） |
| 罰金の引き下げ | 今日から適用 | 明日から適用 |
| 罰金の引き上げ | §7.4 | §7.4 |
| 締切時刻の変更 | 今日から適用 | 明日から適用 |
| 検証方法・パラメータの変更 | 今日から適用 | 明日から適用 |
| 一時休止（01b） | 今日から適用 | 明日から適用 |
| まとめてオフ・削除（73） | 同上 | 同上 |

**例外**: 今日のインスタンスが既に**達成済み**の場合は課金リスクが無いため、6時間前を過ぎていても削除できる。

### 7.3 UI への反映

各操作の確認画面で「今日の分がどうなるか」を明示する。71 が既にこの形式を持っている。

> 締切 08:00 の6時間前を過ぎています。今日はオフにできません（達成できないと ¥500 の課金対象のままです）

16 削除確認ダイアログにも同じ構造の文言が要る。

> 今日 20:00 の分は残ります（達成できないと ¥1,000 の課金対象）。明日以降は作成されません。

**01c / 72b の引き切り削除は確認ダイアログを経由しない。** 引き切りで即削除される導線では上記を伝えられないため、**締切6時間前を過ぎたマイルストーンでは引き切り削除を無効化し、16 の確認ダイアログに倒す**。

### 7.4 罰金の引き上げは別ルール

引き下げは課金回避（性質2の侵害）だが、引き上げは**自傷的な操作**（性質3の侵害）であり、方向が違う。

認証意思決定記録 §1.5-2 は「**新規作成と金額引き上げは翌日以降の発効**」を求めている。これを採用すると、引き上げは常に翌日発効となり、6時間ルールとは独立に適用される。

**採否は要決定**（§10 #5）。採用する場合、勢いで高額を設定した直後に「明日から有効になります」と表示する必要があり、**画面またはシートの新規作成が必要**。

### 7.5 6時間という値

71 が既に採用している値なので踏襲する。ただし締切 07:30 のマイルストーンでは前日 01:30 が境界になり、実質「前日の夜には確定している」ことを意味する。

**最も鋭いのは起床系**（37 のプリセットの既定は 08:00）。当日の免除が必要になりやすい状況（体調不良・眠れなかった夜）が、まさに境界を過ぎた 02:00 以降に発生する。71 は既にこの挙動で作られているため削除に広げるのは一貫しているが、**締切時刻によって猶予を変える**（早朝の締切だけ短くする等）選択肢は残る（§10 #6）。

### 7.6 作成側にガードは設けない（2026-08-17 決定）

新規作成に締切までの下限は設けない。締切の10分前に新しいマイルストーンを作ることもできる。

**削除して作り直すことで金額を引き下げられるのではないか**、という懸念は成立しない。§7.2 の凍結は「今日のインスタンスを削除させない」ものであり、定義を消しても**今日の分は課金対象として残る**。作り直した安いマイルストーンは元の置き換えではなく、別のインスタンスが1件増えるだけである。

締切直前に高額のマイルストーンを作る行為は、回避ではなく自傷にあたる（PRD-00 §1.1 の性質3）。これは金額の上限（§10）と、必要なら翌日発効ルール（§7.4）で扱う問題であり、作成そのものを制限する理由にはならない。「今から30分以内にジムに行く」のような直前の設定は正当な使い方である。

## 8. カード未登録との関係（PRD-01 §6 の帰結）

- オンボーディングを完走したユーザーは初回1件をカード未登録で作成できる
- 2件目以降、およびスキップしたユーザーの作成は **56 でブロック**
- 初回マイルストーンの締切までにカードが登録されなかった場合、**締切前に自動的にオフにする**（PRD-01 §6.3 案 A）
- ホームにカード未登録の警告表示が要る（**新規**）

## 9. 受け入れ基準

### 9.1 モデルと作成

- [ ] 定義とインスタンスが別のものとして扱われ、課金がインスタンス単位で記録される
- [ ] 繰り返しありの定義は、開始日以降、指定曜日にインスタンスが生成される
- [ ] 繰り返しなしの定義は、締切日に1件だけインスタンスを持つ
- [ ] 日付欄のラベルが、繰り返しの有無で「開始日」「締切日」に切り替わる
- [ ] 締切日に今日より前の日付を選べない
- [ ] 罰金額が ¥100 未満・¥50,000 超で作成できない
- [ ] 作成の最終画面で「何を・いつまでに・いくら」が同時に見えている

### 9.2 締切ガード

- [ ] 締切6時間前を過ぎた後、今日のインスタンスの罰金額・締切時刻・検証方法が変更できない
- [ ] 締切6時間前を過ぎた後に削除しても、今日のインスタンスは課金対象として残る
- [ ] 締切6時間前を過ぎた後に削除しようとすると、今日の分が残ることが確認画面に表示される
- [ ] 締切6時間前を過ぎたマイルストーンは、引き切り削除では消えず確認ダイアログに倒れる
- [ ] 73 のまとめて削除・まとめてオフにも同じルールが適用される
- [ ] 今日のインスタンスが達成済みの場合は、6時間前を過ぎていても削除できる
- [ ] マイルストーンを削除した直後に、同じ内容を安い罰金額で作り直しても、当日の課金は回避できない

### 9.3 一覧・ホーム

- [ ] 一覧の行に、オフの発効日が今日か明日かが区別して表示される
- [ ] 01d の完了リストに、達成時刻または課金額が表示される
- [ ] 18 の空状態からの作成が、カード未登録のとき 56 でブロックされる
