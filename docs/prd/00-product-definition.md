## 1. プロダクト定義

**SwitchMe は、ユーザーが自分で設定した行動目標を締切までに実行したことをスマートフォンで検証し、実行できなかった場合に自分で設定した金額を自動的に課金するサービスである。**

一般的な習慣アプリとの違いは、達成を記録するのではなく **未達成に金銭的コストを発生させる**点にある。したがってプロダクトの中心的な品質は「記録の正確さ」ではなく、**課金の妥当性**である。誤判定による課金と、回避可能な課金の両方が致命的な欠陥になる。

### 1.1 プロダクトが守るべき3つの性質

| # | 性質 | 破れたときに起きること |
|---|---|---|
| 1 | **課金は必ず正当な未達成に対してのみ発生する** | 誤課金。返金対応とアンインストール |
| 2 | **達成していない行動を達成扱いにできない** | ペナルティが機能せず、プロダクトの前提が崩れる |
| 3 | **ユーザーが意図しない金額を負わない** | 高額設定の事故。消費者保護上の問題 |

3 は認証やバリデーションでは解けず、金額上限・発効遅延・締切前操作の禁止といった**ルール**で実装する（§7）。

## 2. v1 のプラットフォームスコープ

**v1 は スマートフォンのブラウザ（PWA）を対象とする。** ネイティブアプリは Phase 2 とする。

### 2.1 この選択から確定する制約

`ui.pen` の NOTE「認証の位置（Web v1 / ネイティブ）」および認証意思決定記録 §1.7 に基づく。

| 項目 | v1（Web PWA）での扱い |
|---|---|
| ログイン | **初回必須**。マイルストーン作成より前 |
| 位置情報 | 検証実行時に**フォアグラウンドで取得**（Geolocation API） |
| バックグラウンド検証・自動達成 | **提供しない**。ユーザーが締切前にアプリを開いて検証を実行する |
| プッシュ通知 | PWA としてホーム画面に追加された場合のみ。**インストール導線が実質必須** |
| ライブアクティビティ / Dynamic Island / Watch | 対象外（画面 79〜82 は Phase 2） |
| 決済 | Stripe を直接利用できる（App Store の IAP 制約を受けない） |

### 2.2 ログインが v1 で必須である理由

ブラウザには識別子を永続化できる場所がない。Safari の ITP により、サイト未訪問が数日〜1週間続くと localStorage も Cookie も破棄される。**課金処理はサーバー側で動き続けるため**、アカウントに到達できなくなったユーザーはカードを外すことも退会することもできないまま課金され続ける。これが v1 でログインを遅延させられない理由である。

### 2.3 自動達成の位置づけ

位置情報のバックグラウンド取得による自動達成は、**Phase 2 でも最後に着手する**。v1・Phase 2 前半を通じて、検証は常にユーザーの明示的な操作で行われる前提で設計する。

## 3. コアコンセプト

### 3.1 マイルストーン

ユーザーが設定する「いつまでに・何を・できなければいくら」の単位。

| 属性 | 値 | 由来 |
|---|---|---|
| タイトル | 自由入力（例「ジムでトレーニング」） | 03 |
| 検証方法 | 出発 / 到着 / 写真 / コード のいずれか1つ | 03 / 37 / 38 |
| 検証パラメータ | 検証方法ごとに異なる（§4） | 03 / 75 / 76 |
| 締切日 | 今日 / 明日 / 日付を選ぶ | 03 / 63 / 66 / 67 |
| 締切時刻 | 時刻（例 20:00） | 03 / 54 |
| 繰り返し | 平日 / 週末 / 曜日の個別指定 | 03 |
| 罰金額 | ¥100 / ¥500 / ¥1,000 / カスタム（¥100〜¥50,000） | 03 / 55 |
| 状態 | 実行中 / 休止中 / 完了 | 52 / 70 |

### 3.2 1日のライフサイクル

```
作成 → （繰り返しなら毎日インスタンス化）
     → 締切前: ユーザーが検証を実行
          ├ 判定 OK  → 達成
          └ 判定 NG  → 締切まで再試行可（45）
     → 締切到達（未検証 or 未達成のまま）
          → 未達成が確定 → サーバーが課金
```

判定は**サーバーが証跡（写真・位置ログ・コード）から行う**。クライアントの「達成しました」という申告は信用しない。これはユーザー本人による回避を防ぐための必須条件であり、v1 から適用する。

### 3.3 作成の2モード

| モード | 画面 | 内容 |
|---|---|---|
| 簡単 | 37 → 38 / 38a〜38f | 7種のプリセットアクションから選び、値が埋まった状態で調整 |
| 詳細 | 03 | 全項目を自分で設定 |
| テンプレ手順 | 63 → 57 → 58 → 59 | 日付 → 時間 → 場所/撮影対象/コード → 罰金 の4ステップ |

簡単モードのプリセット（37）:

| アクション | 検証方法 |
|---|---|
| 起床する | 出発 |
| ジムに行く | 到着 |
| 朝の準備を終える | 写真 |
| 作業場所へ移動する | 到着 |
| 作業を始める | 写真 |
| シャワーを浴びる | 写真 |
| 就寝準備をする | 写真 |
| 自分で作る | → 詳細モードへ |

**最終確認画面（38）では「何を・いつまでに・いくら」が同時に見えていなければならない。** 金額を単独ステップに隔離するウィザードにすると、コミットメント全体を把握しないまま確定してしまう。これは認知負荷ではなく契約の可視性の要件であり、他の理由で覆さない。

## 4. 検証方法

4種すべてに共通して、**判定はサーバー側で行い、証跡を保存する**（課金明細 48 が証跡を参照するため）。

### 4.1 出発

指定地点から一定距離以上離れたことを検証する。用途は起床確認（自宅から離れる）。

- パラメータ: 基準地点、距離
- v1: 検証実行時にフォアグラウンドで現在地を取得（05「現在地で検証」）

### 4.2 到着

指定地点の半径内に入ったことを検証する。用途はジム・作業場所への移動。

- パラメータ: 地点（39 場所選択マップ / 58 で設定）、半径（既定 150m）
- 05 の表示は「エニタイムフィットネス渋谷 / 120m」で、現在地と目標地点の距離を提示する
- **滞在時間の検証は現行 UI に存在しない。** projectbrief にあった「45分以上滞在」は v1 では扱わない（Web ではフォアグラウンド前提のため成立しない）

### 4.3 写真

指定された撮影対象が写っているかを画像認識で判定する。

- パラメータ: 撮影対象（75 で選択）
- 撮影対象の候補（75）: 部屋・寝室（ベッド / デスク / 部屋の照明）、水まわり（洗面台 / シャワー / 歯ブラシ）、外出・運動（玄関 / ジム機器 / シューズ）、食事（食事 / お弁当 / プロテイン）
- フロー: 02 案内 → 43 撮影 → 44 プレビュー・送信 → 判定 → 46 達成 / 45 失敗・再試行
- 失敗時は理由を提示する（45「洗面台が写っていません」）

### 4.4 コード

事前に登録したバーコード / QR コードと一致するかを判定する。

- 事前登録: 76 でコードを読み取り登録（例「ザバス ホエイプロテイン / JAN 4902777 310527」）
- 検証: 06 で同じコードを読み取り、登録済みコードと一致するか判定
- 用途: 特定の物品を実際に手に取ったことの証明（プロテインを飲む等）

この方式は「登録済みの値と一致するか」しか見ないため、**同一商品であれば誰の手元のものでも通り、バーコードを撮影した画像でも通る**。手段の性質であって不具合ではないが、判定の強度は写真検証より低い。実績画面（04）の検証方法別の達成率がコードだけ 61% と低いのは、読み取りの失敗率を示していると読める。PRD-03 で読み取り失敗と回避の両面を扱う。

### 4.5 検証を実行できない状態

19（検証エラー）が扱う。位置情報オフ / ネットワークオフライン / 省電力モードによる精度低下を個別に提示し、「このまま期限切れ」になった場合の金額と残り時間を明示する。**復旧手段を提示しないまま課金することは許されない。**

## 5. 課金モデル

### 5.1 基本

- 課金は**未達成が確定した時点でサーバーが実行する**。クライアントからは叩かない（アプリを開かなければ回避できてしまうため）
- カード情報は Stripe SDK でクライアントから直接 Stripe に送る。サーバーはカード番号を保持しない
- **カード未登録ではマイルストーンを作成できない**（56 でブロック）

### 5.2 金額

| 項目 | 値 | 由来 |
|---|---|---|
| プリセット | ¥100 / ¥500 / ¥1,000 | 03 / 59 |
| カスタム範囲 | ¥100 〜 ¥50,000 | 55 |
| 課金単位 | マイルストーン1件の1回の未達成につき1回 | 48 |

### 5.3 課金失敗時（20）

- 自動再試行は**最大3回**
- 再試行間隔は日単位（例「次回の自動再試行 8月10日 09:00」）
- **3回失敗するとマイルストーンの新規作成が停止される**
- ユーザー操作として「支払い方法を更新」「今すぐ再試行」を提供
- カード期限切れの事前検知は 50 で扱う

### 5.4 履歴と明細

- 10 課金・支払い履歴: 月次のペナルティ合計、前月比、達成分も含む時系列リスト
- 48 課金明細（1件）: 金額 / マイルストーン名 / 未達成日時 / 判定結果 / 検証方法 / 支払い手段 / 状態 / **証跡**
- 証跡を明細から参照できることは、誤課金への異議申し立ての前提になる

### 5.5 異議申し立て

**独立した画面は存在しない。** 65 問い合わせが「種類=課金のこと」＋「関連するマイルストーン」で異議申し立て窓口を兼ねている。65 は「通常2営業日以内に登録メールアドレスへ返信します」と既に約束しているため、**返信できる体制がないまま v1 を出すことはできない**。

## 6. 一時停止（オフ期間）

正当な免除経路がないペナルティアプリは、ユーザーが解約で逃げる。**v1 に含める。**

- 選択肢（70）: 1日オフ / 3日オフ / 1週間オフ / 常にオフ（再開するまで停止）
- オフの間は**検証も課金も行われない**
- **締切の6時間前を過ぎると当日はオフにできない**（71）。その旨と、達成できない場合の金額を明示する

## 7. 安全弁

§1.1 の性質 2・3 を守るためのルール。UI に既に実装されているものと、未実装のものを分ける。

### 7.1 UI に実装済み

| ルール | 画面 |
|---|---|
| 締切6時間前を過ぎたら当日オフ不可 | 71 |
| カード未登録では作成不可 | 56 |
| カスタム罰金の上限 ¥50,000 | 55 |
| 課金失敗3回で作成停止 | 20 |

### 7.2 未実装・要決定

認証意思決定記録 §1.5 / §1.6 で挙げられているが、UI にまだ反映されていないもの。

| # | ルール | 状態 |
|---|---|---|
| 1 | **締切直前のマイルストーン削除・金額引き下げの禁止** | **欠落を確認済み**（下記 §7.3） |
| 2 | 1日あたり・月あたりの課金上限 | 46 に「今月の課金リスク ¥2,400 / ¥8,000」の表示があるが、これは**予測額の提示**であって上限として機能しているかは未定義 |
| 3 | 金額引き上げ・新規作成の翌日発効 | 未実装。自傷的な高額設定の抑止として検討 |
| 4 | 一定期間アプリからの通信がなければ全マイルストーンを自動停止 | 未実装。端末の紛失・破損時の出口。検証できない以上、未達成として課金する根拠がない |
| 5 | マイルストーン作成・金額引き上げ時の通知 | 未実装 |

**1 は v1 のブロッカーとして扱う。** 2〜5 は PRD-02 / PRD-04 で扱う。

### 7.3 締切前の回避経路（確認済みの欠落）

締切直前の操作に対するガードは、**オフ期間にしか存在しない**。UI を確認した結果は以下の通り。

| 操作 | 画面 | 締切によるガード |
|---|---|---|
| オフにする | 70 / 71 | **あり**。締切6時間前を過ぎたら当日は不可 |
| スワイプで削除 | 01b / 01c / 72b | **なし** |
| 削除の確認 | 16 | **なし**。「この操作は取り消せません」と、失うもの（連続達成記録 3日 / 検証履歴 46件 / 回避した金額 ¥4,800）を提示するが、締切までの残り時間には触れていない |
| 罰金額の引き下げ | 40 | **なし**。締切直前でも保存できる |
| 一時休止 | 01b のスワイプ | **なし**（70 のシートを経由するかは PRD-02 で確認） |

現状の UI では、8:00 締切のマイルストーンを 7:59 にスワイプ削除すれば課金を回避できる。オフ期間だけ塞がれていて削除と金額引き下げが開いているのは非対称であり、**この穴が残ったままではペナルティの仕組みが成立しない**。

16 が提示している「回避した金額」は、削除の抑止としてはよく機能する設計だが、抑止であって制約ではない。PRD-02 で以下を決める。

- 締切前の削除・金額引き下げをどこから禁止するか（6時間で揃えるか、別の閾値にするか）
- 禁止する代わりに何を許すか（当日分は課金対象のまま残し、翌日以降を削除するなど）
- 金額の引き上げを翌日発効にするか（§7.2 #3 と合わせて決める）

## 9. 用語

| 用語 | 定義 |
|---|---|
| マイルストーン | 「いつまでに・何を・できなければいくら」の設定単位 |
| 検証 | ユーザーが証跡を提出する操作（撮影・現在地取得・コード読み取り） |
| 判定 | サーバーが証跡から達成/未達成を決める処理 |
| 証跡 | 判定の根拠となるデータ（写真・位置ログ・読み取ったコード） |
| 達成 / 未達成 | 判定の結果。未達成の確定が課金の条件 |
| ペナルティ | 未達成に対して課金される金額 |
| オフ期間 | 検証も課金も行われない停止期間 |
| ストリーク（連続） | 連続で達成した日数。46 / 49 で表示 |
| 撮影対象 | 写真検証で写っている必要があるもの（75 で選択） |
| 登録コード | コード検証で照合される、事前登録済みのバーコード / QR（76） |

## 10. オープンリスク

| # | リスク | 影響 | 扱い |
|---|---|---|---|
| 1 | **ブラウザではカメラ直撮りを「強制」できない** | `<input capture>` は端末へのヒントであって強制ではなく、`getUserMedia` のフレームにもカメラ由来である証明は付かない。過去の写真や画面の再撮影を完全には排除できない | ネイティブでも原理的に完全ではなく程度の差でしかないため、v1 の判断は「**どの緩和策を十分とみなすか**」になる。候補: サーバー発行の nonce と撮影セッションの紐づけ、提出までの時間制限、ギャラリー選択経路を設けない、同一画像の再提出検出。閾値は PRD-03 で決める |
| 2 | PWA プッシュ通知の到達性 | 締切前の催促が届かないと未達成が増え、意図しない課金が増える方向に働く | PRD-01 / PRD-06。インストール導線を必須とする |
| 3 | ITP によるセッション消失 | 再ログイン導線が機能しないとアカウントに到達できなくなる | PRD-01 |
| 4 | 課金の法的要件 | 特定商取引法の表示、返金ポリシー（64）、消費者保護 | PRD-05。**ローンチ前に必要** |
| 5 | 問い合わせへの返信体制 | 65 が「2営業日以内に返信」と約束済み。返信できないと信頼を失う | PRD-05 |
| 6 | Phase 2 でネイティブ化する際、ペナルティ課金が App Store の IAP 対象と判断される可能性 | 課金・認証・問い合わせの設計全体に影響する | Phase 2 着手前に確認。**v1（Web）では発生しない** |
| 7 | 誤判定による課金 | プロダクトの信頼を直接損なう | PRD-03（判定の閾値）・PRD-04（異議申し立てと返金） |
