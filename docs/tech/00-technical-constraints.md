## 0. この文書について

### 0.1 位置づけ

PRD が確定させた要件から、**実装がどうであれ満たさなければならない技術的性質**を抜き出す。サービスの比較と選定は [TECH-01](./01-service-selection.md) が扱う。本書は選定の入力であり、特定の製品名を前提にしない。

### 0.2 記法

| 記号 | 意味 |
|---|---|
| **制約** | PRD が確定させた要件から導かれ、選択の余地がないもの |
| **提案** | 本書で新たに提案するもの。PRD には書かれていない |
| **未決** | 判断が要るもの。§14 に集約する |

すべての制約に根拠となる PRD の節番号を付ける。根拠のない主張は書かない。

### 0.3 情報源の優先順位

[PRD-00 §0.1](../prd/00-product-definition.md) を引き継ぐ。本書は PRD の下位にあり、**PRD の記述と矛盾する制約を本書で作らない**。PRD の前提そのものが技術的に誤っている箇所は §13 に分離して記録する。

## 1. 2つの実行経路 — 同期判定と非同期課金

**本書で最も重要な制約。** PRD は正反対の要求を持つ2つの経路を定めている。これを「どちらもキューで処理する」とまとめると、判定側が壊れる。

| | 判定 | 課金 |
|---|---|---|
| 根拠 | [PRD-03 §2.3](../prd/03-verification.md) | [PRD-04 §2.1](../prd/04-billing-and-records.md) |
| PRD の記述 | 「判定は送信直後に完了している必要がある。**非同期のキューに載せて後で通知する設計は取れない**」 | 「締切の瞬間に大量のインスタンスが同時に確定するため、**決済はキューで順次処理される**」 |
| 起動 | ユーザーの送信操作 | サーバーのスケジューラ |
| 応答 | **同期**。数秒以内に 46a2 / 45 を返す | **非同期**。結果は通知で伝える |
| 待っている人 | **いる**（画面の前でユーザーが待つ）→ レイテンシが要件 | **いない** → レイテンシは要件でない |
| 到達の分布 | 締切前の窓に広がる（08:00 締切なら 06:00〜08:00） | 締切時刻の一点に集まる |
| 失敗時 | ユーザーが再試行する（回数無制限） | サーバーが再試行する（最大3回、日単位） |
| 二重実行の被害 | **無い**（同じ写真を2回判定しても結果が同じで、金が動かない） | **ある**（¥500 が ¥1,000 になる）→ 冪等性が必須 |

### 1.1 「到達の分布」は負荷の話ではない

想定される規模では**どちらも負荷にならない**。100人・1日200インスタンスなら、08:00 に確定する課金はせいぜい10件程度である。

この行が意味するのは容量ではなく、**課金が判定を待たせうる**ということだけである。締切時刻に決済 API の呼び出しがまとまって発生し、1件あたり数秒かかりネットワークエラーで再試行もする。**そのとき判定 API の応答が遅くなってはいけない**（判定には画面の前で待っている人がいる）。

これは「課金のほうが件数が多い」という主張ではない。**遅くてよい処理と、遅くてはいけない処理が同じ資源を取り合わないようにする**という、それだけの話である。

### 1.2 帰結

1. 判定経路は**外部 API の同期往復が数秒以内に閉じること**が必須条件になる。バッチ専用・非同期専用の画像認識 API はこの時点で候補から外れる
2. 判定経路に**コールドスタートを持ち込めない**。scale-to-zero 構成は、判定 API に対しては起動遅延がそのまま 44b（判定中）の待ち時間になる
3. **課金経路は再入可能（何度実行しても結果が1回分にとどまる）でなければならない**。→ §1.3
4. **判定と課金の並行度の上限を別々に持つ**。→ §1.4

### 1.3 「再入可能」とは — 課金だけに冪等性が要る理由

**課金の実行は、途中で中断したかどうかを事後に判別できない。**

```
1. 課金レコードを「保留」にする
2. Stripe に PaymentIntent を作る   ← ここでプロセスが落ちる / タイムアウトする
3. 応答を見て「確定」にする
```

2 でタイムアウトした場合、**Stripe 側で課金が成立したかどうかがこちらから分からない**。レコードは「保留」のまま残る。次のポーリングがこの行を拾って再実行すると、**同じインスタンスに2回課金されうる**。

同じことが次の経路でも起きる。

| 経路 | 再実行が起きる理由 |
|---|---|
| プロセスの再起動 | デプロイ・OOM・クラッシュ。処理中だった行が「保留」で残る |
| ネットワークのタイムアウト | 応答が返らなかっただけで、相手側では成立している可能性がある |
| スケジューラの二重取得 | 排他が漏れると2つのワーカーが同じ行を拾う（`SKIP LOCKED` で防ぐ、§4.3） |
| Stripe webhook の再送 | webhook は**同じイベントを複数回送る**。§8.2.2 |

**対策**: 決済 API を呼ぶときに**インスタンスID を冪等キーとして渡す**（PRD-04 §2.2）。決済サービス側が「このキーは処理済み」と判断して、2回目以降は最初の結果をそのまま返す。**こちら側で「もう課金したか」を判定する必要がなくなる。**

**判定側にこれが要らない理由**

- 同じ写真を2回判定しても、**返る結果が同じで、金が動かない**。損失がない
- そもそも**再試行は別の判定として扱うのが仕様**である（PRD-03 §5、回数無制限）。ユーザーが撮り直したら、それは新しい証跡に対する新しい判定であって、重複ではない。ここで重複排除をかけると仕様に反する
- 判定にも重複を防ぐ仕組みはある（nonce、PRD-03 §4.3 #2）が、**目的が違う**。あれは「同じ nonce で複数枚を出させない」という真正性の対策であって、二重課金の防止ではない

### 1.4 「並行度を分ける」とは

同時に走らせる本数の上限を、判定と課金で**別々に持つ**、という意味である。

```
判定: 同時 N 本まで（ユーザーが待っているので、空きが常にある状態を保つ）
課金: 同時 M 本まで（誰も待っていないので、少なくてよい）
```

これを1つの上限にまとめると、締切時刻に課金が上限を埋め、**写真を送ったユーザーが空き待ちで止まる**。上限を分ければ、課金がいくら詰まっても判定側の空きは減らない。

実装としては「別のマシンを立てる」必要はない。**同じプロセスの中で、課金ワーカーの並行数に上限をかける**だけで足りる（セマフォ、専用のタスクグループなど）。規模が大きくなったときに初めてプロセスやマシンを分ける。

## 3. 認証・セッション

根拠: [PRD-00 §2.2](../prd/00-product-definition.md) / [PRD-01 §3](../prd/01-onboarding-auth.md) / [PRD-06 §5.2](../prd/06-notifications.md)

### 3.1 制約

**PRD-01 §3.1 / §2.2 のまま。** 一度は「Google のみ必須」「未ログインでも閲覧可」に変更する決定をしたが、**2026-08-18 に撤回して元に戻した**（理由は §3.5）。

| # | 制約 | 根拠 |
|---|---|---|
| 3.1.1 | 提供する手段は Google / Apple / メール+パスワード（8文字以上）の3つ。X は提供しない | PRD-01 §3.1 |
| 3.1.2 | ソーシャルログインは**メールアドレスの一致ではなく、提供元の安定した識別子（`sub`）で同一ユーザーに解決する** | PRD-01 §3.2-3。理由は §3.3 |
| 3.1.3 | メール+パスワード登録は**メール確認を完了するまでオンボーディングを進めない**。ソーシャルは追加確認を行わない | PRD-01 §3.3 |
| 3.1.4 | セッションが無効な状態でどの URL にアクセスしても 12 ログインに到達する。白画面・エラーで止まらない | PRD-01 §8.1 |
| 3.1.5 | **ログインはウォークスルー（33）の直後に必須。** マイルストーン作成より前 | PRD-00 §2.2 / PRD-01 §2.2 |
| 3.1.6 | 通知・メールのリンクをタップしたとき、未ログインならログインを挟み、**ログイン後に元の遷移先へ復帰する** | PRD-06 §3.3 |
| 3.1.7 | メール経由でアカウントへ復帰できる経路が要る。**専用のワンタイムリンク画面を新規に作るかは選択できる**（§3.4） | PRD-01 §3.2-4 / PRD-06 §5.2 |
| 3.1.8 | ログイン手段が1つしかないとき、それを解除できない | PRD-05 §4.3 |
| 3.1.9 | Apple の「メールを非公開」に返信するには、Apple Developer の Email Communication にドメイン登録と SPF 公開が要る | PRD-01 §3.1 |

### 3.2 ITP に対する設計（PRD の前提を一部緩和できる）

[PRD-00 §2.2](../prd/00-product-definition.md) は「ITP により、サイト未訪問が数日〜1週間続くと localStorage も Cookie も破棄される」としている。**Cookie についてはこれを回避できる。**

WebKit の 7日上限は **`document.cookie`（JavaScript）で書いた Cookie** に適用される。サーバーが `Set-Cookie` ヘッダーで発行し `Secure` + `HttpOnly` を付けた Cookie は対象外である（[WebKit ITP 2.1](https://webkit.org/blog/8613/intelligent-tracking-prevention-2-1/) / [Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)、確認日 2026-08-18）。

**制約 3.2.1**: セッションは**サーバー発行の `HttpOnly` + `Secure` + `SameSite=Lax` Cookie** で持つ。認証トークンを localStorage や `document.cookie` に置く構成は採らない。

一方、ITP 2.3 は**7日間の未訪問で script-writable storage を削除する**。ここには localStorage / IndexedDB / Cache API に加えて **Service Worker の登録**が含まれる（[ITP 2.3](https://webkit.org/blog/9521/intelligent-tracking-prevention-2-3/)、確認日 2026-08-18）。したがって:

**制約 3.2.2**: 未訪問が続くと**プッシュ購読は失効しうる**。PRD-06 §5.3 の「410 Gone を検知して再購読を促す」は、例外的な事故ではなく**通常起きる事象**として実装する。**§5.11 の穴3 はこれが原因である。**

### 3.3 アカウントの同一性

#### 3.3.1 なぜメールアドレスで同一ユーザーに解決してはいけないか（3.1.2 の理由）

メールアドレスの変更への対応は理由の**一部**であって、主な理由ではない。

| # | 理由 | 起きること |
|---|---|---|
| 1 | **メールアドレスは変わる** | Google Workspace のアドレス変更、独自ドメインの移行。同じ人が別人として扱われ、**課金履歴とマイルストーンに到達できなくなる** |
| 2 | **メールアドレスは一意な本人確認にならない** | 別の認証手段で「同じメールアドレスを持っている」と主張されたとき、メールで照合していると**同一ユーザーとして解決してしまう**。提供元がそのアドレスを検証しているとは限らない |
| 3 | Apple の「メールを非公開」 | 発行される `@privaterelay.appleid.com` はアプリごとに異なり、実アドレスと結びつかない |

**2 がアカウント乗っ取りの経路になる。** 3手段を提供する構成では、同じメールアドレスを Google と メール+パスワード の両方で名乗れるため、**この経路は実在する**。

**制約**: 提供元の `sub`（アカウントに固有で、メールアドレスを変えても不変な識別子）を主キーとして保持する。メールアドレスは**表示と連絡先としてのみ**扱い、変更されたら更新する。

#### 3.3.2 同じメールアドレスで別の手段からログインしてきた場合（決定: 案 B）

3手段を提供する以上、同じメールアドレスを Google・Apple・メール+パスワードのどれからでも名乗れる。放置すると、Google で登録したユーザーがメール+パスワードで「新しいアカウント」を作り、**マイルストーンも課金履歴も見えない状態で二重に課金される**。

**決定（2026-08-18）: 案 B — 既存アカウントへ誘導する。** ログイン画面で「このメールアドレスは Google で登録されています」と示し、元の手段に戻す。

#### 前提が変わった: アカウントの結合は既定で起きる

Supabase Auth を使う場合、**同一メールアドレスのアイデンティティは既定で自動的に1ユーザーへリンクされる**。

> Supabase Auth automatically links identities with the same email address to a single user.
> It would also be an insecure practice to automatically link an identity to a user with an unverified email address
> — [Supabase / Identity Linking](https://supabase.com/docs/guides/auth/auth-identity-linking)（2026-08-18 取得）

**リンクは検証済みメールアドレスに限られ、未検証のアイデンティティは対象にならない。** これは、自前実装したときに最も誤りやすい箇所（検証状況の確認漏れが乗っ取りになる）を、認証基盤が先に押さえているということである。

**帰結**

| | 内容 |
|---|---|
| **二重アカウント → 二重課金は既定で起きない** | Google で登録した人が同じアドレスでメール+パスワードを使っても、確認メールを踏んだ時点で同じユーザーに結合する。B が防ごうとしていた被害は、既定挙動が先に防いでいる |
| **案 B の位置づけが変わる** | B は安全弁ではなく **UX** になる。「パスワードが違います」ではなく「このメールアドレスは Google で登録されています」と返す、ログイン画面の振る舞いである |
| **案 A（アカウントを分ける）は実質選べない** | 自動リンクを無効化する方法が公開ドキュメントに記載されていない（2026-08-18 時点） |
| **PRD-01 §3.3 のメール確認必須に技術的な裏付けが付いた** | 「メール+パスワード登録はメール確認を完了するまで進めない」（3.1.3）は、UX の判断であると同時に、**自動リンクが安全に働くための条件**でもある。ここを緩めてはいけない |

#### 制約

**制約 3.3.2.1**: ログインが失敗したとき、**そのメールアドレスに紐づく登録済みの手段を提示する**。「パスワードが違います」で止めない。

**制約 3.3.2.2**: 逆方向も塞ぐ。**Google / Apple でサインインしてきたアドレスが既にメール+パスワードで登録済みの場合も、同じ案内を出す**。片方向だけ実装すると、もう片方で同じ迷いが起きる。

**制約 3.3.2.3**: この案内は**アカウントの存在を漏らす**。任意のメールアドレスを入力して登録有無を確かめられるため、**レート制限を必須とする**。消費者向けサービスでは一般的なトレードオフだが、無防備にはしない。

**制約 3.3.2.4**: `ui.pen` の 12 ログインに、この案内の表示が要る（§13.2 #8）。**現行の 12 に該当する表示は存在しない。**

#### 救えない残存リスク: Apple の「メールを非公開」

Apple の「メールを非公開」で発行される `@privaterelay.appleid.com` は**実アドレスと一致しない**。したがって:

- 同じ人が **Apple（非公開）で1アカウント、Google で1アカウント**を持ちうる
- **メールアドレスが違うので自動リンクは働かず、案 B の案内も出せない**（照合するアドレスが存在しない）
- 両方でマイルストーンを作れば、**同一人物が二重に課金される**

**これは案 A / B / C のどれを選んでも解決しない。** 検知する手段が無い。

**扱い**: 発生頻度は低い（Apple で登録した人が、後日わざわざ Google でも登録する場合に限る）ため、v1 では受け入れる。実際に問い合わせが出たら 65 で個別に対応する（§14 #9）。

### 3.4 ワンタイムリンク専用の画面は、作らなくても要件を満たせる

PRD-01 §11 #9 と PRD-06 §11 #5 は「**ワンタイムリンクでのログイン画面**」を**新規画面**として要求している。根拠は PRD-01 §3.2-4「セッションが切れていてもカード停止・退会に到達できる経路」である。

**満たすべきは経路であって、画面ではない。** 手段ごとに、既存の仕組みだけで復帰できるかを見る。

| 登録手段 | セッションが切れた後の復帰 | 新規画面が要るか |
|---|---|---|
| Google / Apple | アプリを開いて「Google で続ける」を1タップ。**ユーザーは常に自分のアカウントを持っており、失うものがない** | **要らない** |
| メール + パスワード（覚えている） | 12 ログインで入る | **要らない** |
| メール + パスワード（忘れた） | **34 パスワードリセット**でメールのリンクを受け取り、再設定して入る | **要らない**（34 は既に設計済み） |

**34 パスワードリセットが、既にメール経由のアカウント復帰経路になっている。** ワンタイムリンクとの差は「新しいパスワードを設定する1ステップが挟まるか」だけであり、**新しい能力ではなく手数の差である**。

**制約 3.4.1**: 課金メールからの復帰は、次で要件を満たす。

```
課金メールのリンク → アプリを開く → 未ログインなら 12 ログイン
                  → Google 1タップ / パスワード / 34 でリセット
                  → 元の画面（48 明細・23 支払い方法・74 退会）へ復帰
```

最後の「元の画面へ復帰」は **3.1.6（通知タップからの復帰）と同じ仕組みで、プッシュ通知のために元々必要**である。**追加実装はここだけで、専用画面は不要。**

**残る摩擦（§14 #10）**: ユーザーが**どの手段で登録したかを覚えていない**場合、12 ログインの前で迷う。ワンタイムリンクはこれを完全に迂回できる。§3.3.2 の案 B（メールアドレスから登録手段を示す）を実装すれば、専用画面なしでも解消する。

**判断**: 専用画面を作るかは**手数の問題であり、要件の問題ではない**。作らない前提で進め、実際の問い合わせが出てから足せばよい。

### 3.5 撤回した変更の記録（2026-08-18）

### 4.3 提案: 予約タイマーではなく due テーブルのポーリングにする

締切6時間前より前の編集で、**締切時刻・罰金額・検証方法・オフ期間が変わる**（PRD-02 §7.2）。予約済みの通知はそのたびに作り直す必要がある。

個別の遅延タイマー（外部キューの delay 指定など）は、予約後のキャンセルと書き換えが難しい。**送信予定を行としてデータベースに持ち、毎分「今送るべき行」を取り出す**方式のほうが、編集のセマンティクスに素直である。

```
notification_schedule(id, instance_id, kind, send_at, sent_at, canceled_at)
  → 毎分 SELECT ... WHERE send_at <= now() AND sent_at IS NULL AND canceled_at IS NULL
                     FOR UPDATE SKIP LOCKED
  → 編集時は該当行を canceled_at で無効化し、作り直す
```

同じ仕組みが課金キュー（§1 の非同期経路）にも使える。`SKIP LOCKED` により、複数ワーカーで並行に取り出しても二重処理が起きない（`.agents/skills/supabase-postgres-best-practices/lock-skip-locked.md`）。

**この方式の副作用**: 毎分データベースにアクセスするため、**アイドル時に停止して課金を止める構成（scale to zero）が成立しない**。データベースの課金が「起動していた時間」に比例するサービスでは、実質的に常時起動として見積もる必要がある（TECH-01 §4）。

### 5.11 課金メールが要る理由は、セッションではなくプッシュの構造的な穴

PRD-06 §5.1 は「金銭に関わる通知はメールでも送る」と決めている。**この根拠を、セッション消失（§3.2 で緩和された）から切り離して整理する。**

メールを削るには、**プッシュが届かない経路をすべて塞ぐ**必要がある。穴は3つある。

| # | 穴 | 塞げるか |
|---|---|---|
| 1 | **iOS でホーム画面に未追加**。通常の Safari タブでは Web Push が動作しない（§2.2） | **塞げる。** PWA インストールを必須化する（現在は 62 の直後に任意で案内）。PRD-01 §5.1 の「必須にしない」を変更することになり、**手順を完了できないユーザーがオンボーディングで詰まる**（PRD-01 §5.1 が必須にしなかった理由そのもの） |
| 2 | **通知権限を拒否している** | **塞げない。** ブラウザの権限はユーザーのものであり、拒否したまま使い続けられる |
| 3 | **7日間の未訪問で Service Worker の登録が消える**（§3.2.2）。登録が消えるとプッシュ購読も失効する | **実質塞げる。** 「一定期間の無通信で全マイルストーンを自動停止」（PRD-00 §7.2 #3）の判定期間を **7日以下**にすれば、購読が死ぬ頃には課金も止まっている |

**3 が最も危険である。** 7日間アプリを開いていないユーザーは、その間もマイルストーンが動いて毎日課金されうるのに、通知だけが止まっている状態になる。**これは「使っていないのに請求される」という、最も苦情になる形である。**

**判断**

| 選択 | 条件 |
|---|---|
| **メールを送る**（PRD-06 §5.1 のまま） | 穴 1〜3 をすべて許容できる。実装は SES で月 $1 未満（TECH-01 §6） |
| **メールを送らない** | 穴1（インストール必須化）と穴3（自動停止を7日以下）を**両方**塞ぐ。**穴2 は残るため、通知権限を拒否したユーザーには何の予告もなく課金される** |

**送る範囲を絞る案（提案）**: 全種類をメールで送るのではなく、次に限る。

| 通知 | メール | 理由 |
|---|---|---|
| 05 課金確定 | **送る** | 請求の告知。消費者保護。プッシュが死んでいても届く唯一の経路 |
| 06 決済失敗 / 07 カード期限切れ / 14 全休止 | **送る** | 対応しないと全マイルストーンが止まる（PRD-04 §3.2.1） |
| 15 再審査の結論 / 16 返金の完了 | **送る** | 申し立てへの回答 |
| 13 カード未登録の警告 | **送る** | 自動オフの予告 |
| **02 直前警告** | **プッシュが届かないユーザーにのみ送る** | 通数が最も多い（PRD-06 §10 #1 の未決の中身）。購読が有効なユーザーにはプッシュで足りる |

**02 を条件付きにすると、メールの通数が大きく下がる**（TECH-01 §6.1 の試算で 3,000通/月 が減る）。61 の「課金の前に必ず通知します」も、届かない人にだけ経路を足す形で維持できる。

**制約 5.10**: Web Push の送信自体に外部サービスの費用は発生しない。VAPID 鍵で署名し、購読の `endpoint`（各ブラウザベンダのプッシュサービス）へ HTTP POST するだけである。**プッシュ通知の SaaS は不要**（TECH-01 §1）。

**ただし費用がゼロでも実装がゼロではない。** VAPID の JWT 署名（ES256）と、ペイロードの ECDH + HKDF + AES-GCM 暗号化が要る。**実行環境にこれを済ませたライブラリがあるかは選定の評価軸になる**（TECH-01 §8.3）。

## 6. 画像判定

### 6.1 制約

| # | 制約 | 根拠 |
|---|---|---|
| 6.1.1 | 判定はサーバーが行う。クライアントの達成/未達成の申告は受け取らない | PRD-03 §2.1 |
| 6.1.2 | **同期で返す**（§1） | PRD-03 §2.3 |
| 6.1.3 | v1 で判定するのは**物体型24種のみ**。状態型・数値型は Phase 2 | PRD-03 §3.1 |
| 6.1.4 | 「その他」（自由入力）は設けない。対象は必ず列挙されたもののいずれか | PRD-03 §3.1 |
| 6.1.5 | 失敗時に**理由を提示する**（「洗面台が写っていません」） | PRD-03 §5 |
| 6.1.6 | 再試行は締切まで回数無制限。ただし30秒に1回のレート制限を設ける | PRD-03 §5 |
| 6.1.7 | 判定にバイアスをかけない。**閾値は1つ**置き、運用開始後に実データで調整する | PRD-03 §4.2 |

### 6.2 6.1.7 が判定技術に課す条件

「閾値を1つ置いて実データで調整する」という設計は、**判定器が連続値のスコアを返し、そのスコアの意味が対象をまたいで安定していること**を前提にしている。

| 判定技術 | 6.1.7 との適合 |
|---|---|
| 物体検出 / ラベル検出モデル | 適合する。確信度は学習時に校正されており、閾値をそのまま乗せられる |
| 汎用の視覚言語モデル（VLM）に「写っていますか」と尋ねる | **適合しない。** 自己申告の確信度は校正されておらず、対象やプロンプトの言い回しで基準が動く |

**この不一致は選定の評価軸に含める必要がある**（TECH-01 §2）。VLM を選ぶ場合、6.1.7 を「単一の閾値」ではなく「単一の判定基準」として読み替える PRD 側の変更が要る（§14 #2）。

### 6.3 24種のうち一般的な語彙で表しにくい対象がある

PRD-03 §3.1 のカタログには **お弁当 / プロテイン / 薬・サプリメント / ヨガマット** のように、汎用のラベル語彙では「Food」「Bottle」「Mat」といった粗い分類にしか落ちない対象が含まれる。

**制約 6.3.1**: 判定技術を選定したら、**24種それぞれについて、その技術で判定可能かを実データで確認する**。判定できない対象が出た場合、v1 のカタログから外すか、別の技術を併用するかを決める（§14 #4）。これはコストではなく**カバーできる習慣の範囲**の問題であり、プロダクトの価値に直結する。

## 7. 真正性

根拠: [PRD-03 §4](../prd/03-verification.md)

### 7.1 写真

| # | 制約 | 根拠 |
|---|---|---|
| 7.1.1 | サーバーが発行した nonce を検証セッションに紐づけ、**その nonce に対応する1枚だけを受け付ける** | PRD-03 §4.3 #2 |
| 7.1.2 | 撮影から送信までの時間を制限する（5分） | PRD-03 §4.3 #3 |
| 7.1.3 | 提出画像のハッシュを保持し、**同一・ほぼ同一の画像の再提出を検出する** | PRD-03 §4.3 #4 |
| 7.1.4 | 撮影時刻とサーバー時刻の乖離を検出する。**クライアントの主張する時刻を信用しない** | PRD-03 §4.3 #5 / §4.4 |
| 7.1.5 | 仮想カメラの差し込みとクライアントコードの改変には対応しない。この抜け道は許容する | PRD-03 §4.3 |

**7.1.3 は暗号学的ハッシュでは実装できない。** SHA-256 は1ビットの差で全く違う値になるため、「ほぼ同一」を検出できない。**知覚ハッシュ（perceptual hash）とハミング距離による近傍検索**が要る。

これはデータ設計に波及する。

```
verification_image(id, user_id, phash BIGINT, submitted_at, ...)
  → 提出時: 同一ユーザーの過去N日分の phash と比較し、
            ハミング距離が閾値以下の行が存在すれば「使い回し」と判定
```

- 保持する行は**証跡の画像本体とは寿命が違う**。画像は30日で消えるが（§9）、使い回し検出のためのハッシュはより長く持つ意味がある（§14 #5）
- 総当たり比較で足りるかは、1ユーザーあたりの保持件数で決まる。30日 × 1日2枚 = 60件程度なら索引なしで足りる。それを超える保持をするなら BK-tree や分割インデックスを検討する
- **画像のデコードとリサイズがサーバー側で必要**になる。判定 API に送る前段の画像処理が、実行環境の選定に効く（TECH-01 §3）

### 7.2 位置

| # | 制約 | 根拠 |
|---|---|---|
| 7.2.1 | `coords.accuracy` を検証し、極端に良すぎる値・悪すぎる値を弾く | PRD-03 §4.4 |
| 7.2.2 | 直近の検証位置との時間差・距離から、物理的に不可能な移動を検出する | PRD-03 §4.4 |
| 7.2.3 | サーバー側で受信時刻を記録する | PRD-03 §4.4 |
| 7.2.4 | IP ジオロケーションとの突き合わせは**採用しない** | PRD-03 §4.4 |

7.2.2 は「直近の検証位置」を保持していることが前提になる。位置証跡の保持期間（90日、§9）とは別に、**直近の判定に使える位置を高速に引ける形で持つ**。

### 7.3 コード

| # | 制約 | 根拠 |
|---|---|---|
| 7.3.1 | 読み取り値だけを送る構成は採らない。**フレーム画像をサーバーに送り、サーバー側で再デコードして判定する** | PRD-03 §4.5 |
| 7.3.2 | 画像は判定後に破棄する | PRD-03 §7.3 |
| 7.3.3 | **読み取り値も保存しない**。保存するのは判定結果（一致 / 不一致）と時刻のみ | PRD-03 §7.3 |
| 7.3.4 | 登録済みコード（76 で登録したもの）はマイルストーンの設定として保存する | PRD-03 §7.3 |

**7.3.1 はサーバー側にバーコード / QR のデコーダが要る**ことを意味する。これも実行環境の選定に効く（TECH-01 §3）。

### 8.2 課金の状態機械

PRD-04 §2.1 が6状態を定めている。**これはそのままデータベースの状態列になる。**

```
保留 ──成功──→ 確定 ──異議申立──→ 再審査中 ──誤検知と判断──→ 返金済み
 │                │                    │
 │                └──返金──────────────→ 返金済み
 │                                      └──認めない──→ 確定
 └──失敗──→ 失敗 ──再試行成功──→ 確定
              └──3回失敗──→ 中止
```

「保留」を独立させる理由（PRD-04 §2.1）: 締切到達と決済 API の応答は同時ではない。この期間を状態として持たないと二重課金と取りこぼしを検知できない。

**制約 8.2.1**: 状態遷移は**データベースのトランザクション内で行い、決済 API の呼び出しはトランザクションの外に置く**。外部 API の応答待ちでトランザクションを開いたままにしない（`.agents/skills/supabase-postgres-best-practices/lock-short-transactions.md`）。

**制約 8.2.2**: Stripe の webhook を受ける経路が要る（決済結果の非同期確定、失敗の検知、返金の反映）。webhook は署名検証と冪等処理が必須で、**同じイベントが複数回届く前提**で書く。

### 8.3 退会と課金の分離

8.1.11 の帰結。

**制約 8.3.1**: 課金レコードは**ユーザーレコードへの外部キーに依存して消える設計にしてはならない**。退会後も課金の実行に必要な最小限（Stripe の顧客ID、金額、対象インスタンスID、通知先メールアドレス）が残る（PRD-05 §5.1）。

**制約 8.3.2**: 認証基盤が管理するユーザーテーブル（外部の認証サービスを使う場合の `users` 相当）と、アプリのユーザーテーブルを**分ける**。課金レコードはアプリ側のユーザーIDだけを参照し、認証基盤のテーブルを参照しない。**退会は論理削除**とし、認証情報の削除は未確定の課金がすべて決着してから行う。

この分離を怠ると、退会時に認証側のレコードを消した瞬間に課金レコードが連鎖して消え、8.3.1 に違反する。**認証を外部サービスに任せる構成では必ず踏む**（TECH-01 §4.3.1）。

この保持は削除請求と衝突しうる。**法務確認の対象**（PRD-05 §10 #4）。

## 10. データモデル

根拠: [PRD-02 §2](../prd/02-milestone-management.md) / [PRD-04 §5.2](../prd/04-billing-and-records.md)

### 10.1 定義とインスタンスを分ける

| 概念 | 内容 | 課金との関係 |
|---|---|---|
| 定義 | 「平日 08:00 までに起床する / ¥500」というルール | 削除・編集の対象 |
| インスタンス | 「8月17日（月）08:00 の起床確認」という1回分 | **課金はインスタンス単位** |

**制約 10.1.1**: 締切6時間前の凍結（PRD-02 §7.2）は、この分離を前提にしている。**定義を削除しても、凍結後の当日インスタンスは課金対象として残る**。したがってインスタンスは定義への外部キーに依存して消えてはならない。

**制約 10.1.2**: インスタンスは締切時刻に**罰金額・締切時刻・検証方法・検証パラメータのスナップショットを持つ**。定義を後から編集しても、確定済みインスタンスの課金額が変わってはならない。

### 10.2 集計指標の定義

PRD-04 §5.2 が定めている。**データモデルはこれを効率的に計算できる形にする。**

| 指標 | 定義 |
|---|---|
| 達成率 | 達成インスタンス ÷ 決着したインスタンス。**オフ期間中のインスタンスは分母に含めない** |
| 合計ペナルティ | 当月に**確定**した課金の合計。保留・失敗中は含めない |
| ストリーク | **2種類ある**。46a2 は定義ごと、49 はアカウント全体 |
| 曜日別 | 直近4週間の、その曜日の達成率 |
| 検証方法別 | 検証方法ごとの達成率 |

**制約 10.2.1**: 「オフ期間中のインスタンスを分母から外す」ためには、**オフ期間中もインスタンスを生成して「オフ」として記録する**か、**生成しないかわりに期間を別に記録する**かのどちらかが要る。前者のほうが集計が単純になる。

### 10.3 時刻の扱い

**制約 10.3.1**: すべての時刻を UTC で保存し、ユーザーのタイムゾーンを別に持つ。締切の「20:00」はユーザーのローカル時刻として入力され、インスタンス生成時に絶対時刻へ解決される。

**制約 10.3.2**: 「一日の開始時刻」（既定 06:00、PRD-05 §3.2）は日付境界の唯一の定義であり、集計・インスタンス生成・ホームの表示すべてがこれに従う。**この値をユーザーが変更したときの既存インスタンスの扱いは未決**（PRD-05 §10 #2）。
