## 0. この文書について

### 0.1 目的

[TECH-00 §12](./00-technical-constraints.md) の R1〜R12 に対して具体的なサービスを比較し、**個人開発として成立する構成**を提案する。

### 0.2 価格の扱い

**この文書のすべての価格は 2026-08-18 に各ベンダーの公式料金ページから取得した。** 取得元は §12 に列挙する。価格は変わる。**判断の前に再確認すること。**

- ブログ・まとめ記事は情報源にしていない
- 為替は **1 USD = ¥150 と仮定する**（未検証の仮定。実レートで再計算すること）
- 記憶から書いた価格は1つも含まれていない

### 0.3 評価軸

| 軸 | 内容 | 重み |
|---|---|---|
| **床** | ユーザーが0人のときの月額固定費 | **最大**。個人開発を殺すのは従量ではなく床 |
| **従量** | §1 の想定プロファイルでの月額 | 中。伸びるのは画像判定だけ |
| **CLI 操作性** | エージェントがコマンドラインだけで構築・変更・デバッグを完了できるか | **高**（2026-08-18 追加） |
| **SDK の成熟度** | 認証・課金・DB・判定・通知の各層に、選んだ言語の公式クライアントがあるか | **高**（2026-08-18 追加） |
| 制約適合 | TECH-00 の R1〜R12 を満たすか | 前提条件。満たさないものは比較しない |
| 運用の重さ | 個人1人で障害対応・バックアップ・更新ができるか | 中 |

**この2軸を入れる理由**: 開発をエージェントに任せる前提では、Web コンソールでしか変更できない設定が**そのままエージェントの手の届かない領域**になる。同じく、公式クライアントが無い層は HTTP を手書きすることになり、**実装量と事故の確率が上がる**（署名・暗号化・冪等性を自作することになるため）。詳細は §8。

| 領域 | 決定 | 根拠 | 費用 |
|---|---|---|---|

### 1.1 Stripe の手数料構造 — プロダクト上の発見

日本国内のカード決済手数料は **3.6%、固定手数料なし**（[stripe.com/jp/pricing](https://stripe.com/jp/pricing)、2026-08-18 取得）。返金時に決済手数料は返らない（標準料金体系ではカード決済の返金に手数料はかからないが、既に取られた決済手数料は戻らない）。

**最小罰金額 ¥100 の経済性は成立する。** 固定手数料が乗る料金体系（例: 米国の 2.9% + $0.30）であれば ¥100 の課金で手数料が ¥45 を超え、罰金の下限そのものを見直す必要があった。日本の 3.6% では ¥100 に対して ¥3.6 であり、下限の設定に影響しない。

**ただし返金には手数料の非対称性がある。** 再審査で誤検知と認めて全額返金した場合（PRD-05 §2.3）、ユーザーには ¥500 が戻るが、事業者側は 3.6%（¥18）を回収できない。誤判定1件あたりの実損は返金額ではなく **返金額 × 3.6%** ではなく、**返金額の手数料分**である。誤判定率が判定技術の選定に効く経路がここにもある。

**想定プロファイルでの手数料**: ¥540,000 × 3.6% = **¥19,440/月**。

**これはインフラ費用より1桁大きい。** ただし課金額に比例する収益連動費用であり、床ではない。個人開発として見るべき数字は §7.1 の床である。

### 1.2 アカウント審査（解決済み）

「ユーザーが自分に課した違約金を事業者が徴収する」という商品性が Stripe の審査を通るかを未検証のリスクとして挙げていたが、**同種の事業で審査を通過しているサービスが複数存在することをユーザーが把握しているため、リスクとして扱わない**（2026-08-18 決定）。

**PRD-04 §7 の法務確認（特定商取引法の表示、ペナルティの課税区分が役務の対価か違約金か）は別の論点として残る。** こちらはローンチの前提条件のままである。

### 2.3 決め手になるのは判定の質のほう

TECH-00 §6.2 / §6.3 で示した2つの論点が実際の選定を決める。

| 論点 | ラベル検出（Vision / Rekognition） | 視覚言語モデル（Gemini / Claude） |
|---|---|---|
| **PRD-03 §4.2 の「閾値は1つ」** | **適合する。** 校正された確信度が返る | **適合しない。** 自己申告の確信度は校正されておらず、対象やプロンプトで基準が動く |
| **24種のカバー**（PRD-03 §3.1） | 一般語彙で表しにくい対象がある（お弁当 / プロテイン / 薬・サプリメント / ヨガマット）。汎用ラベルでは「Food」「Bottle」「Mat」に落ちる。対象ごとにラベル集合を人手で対応付ける作業が発生し、対応できない対象は v1 のカタログから外すことになる | 自然言語で対象を記述できるため、24種をそのまま扱える |
| **失敗理由の提示**（PRD-03 §5） | 検出ラベル一覧から生成できる | 生成させられる |
| **Phase 2 の状態型**（整えたベッド / 空のシンク / 消灯した部屋） | **使えない。** 物体の有無しか判定できない | 扱える |
| **Phase 2 の数値型**（体重計の表示） | OCR を別途組み合わせる | 扱える |

### 2.4 提案: Gemini 2.5 Flash-Lite（VLM）を主案、PRD-03 §4.2 の改訂を伴う

**理由は、カバーできる習慣の範囲が広いことと、Phase 2 に地続きであること。** コストではない。

- 24種のカタログを追加の対応付け作業なしにそのまま扱える。ラベル検出を選ぶと、カタログから落ちる対象が出る可能性が高く、**これはプロダクトの価値を直接削る**
- 状態型（Phase 2）に同じ仕組みで拡張できる。ラベル検出を選ぶと Phase 2 で判定基盤を作り直すことになる
- 最も安い（1,000人時点で $6.4/月）

**代償として PRD の改訂が要る。** PRD-03 §4.2 は「閾値を1つ置き、運用開始後に実データで調整する」としているが、VLM の自己申告の確信度はこの前提を満たさない。次のいずれかに読み替える必要がある（TECH-00 §14 #2）。

| 案 | 内容 |
|---|---|
| A | 判定を **boolean + 理由** の構造化出力にし、「単一の閾値」を「**単一の判定基準（プロンプト）**」と読み替える。調整対象は数値ではなくプロンプトと評価データセットになる |
| B | 対象ごとに**正例・負例の評価データセット（各20枚程度）**を作り、プロンプトを固定した上で確信度の実測分布から閾値を決める。§4.2 の運用は形式上維持されるが、「スコアの意味が対象をまたいで安定している」という前提は成り立たない |

**A を推奨する。** B は校正されていないスコアに閾値を置く構成であり、「実データで調整する」の実体が「プロンプトを変えると閾値も変わる」になって説明できなくなる。

**いずれの案でも評価データセットは要る。** 24種 × 正例負例で 1,000枚程度。これは選定の前提であり、実装前に作る作業として計上する（§11.2 #2）。

### 2.5 対案: Rekognition DetectLabels

PRD-03 §4.2 をそのまま維持したい場合はこちら。校正された確信度が返るため、閾値運用が素直に成立する。

代償は §2.3 の表の通り、**24種のうち何種類がカバーできるかが未知**であり、Phase 2 で作り直しになること。

### 3.3 Cloudflare Workers を同条件で比べる

**Workers を「D1 とセット」で評価すると比較条件が揃わない。** 主案は Supabase Postgres を使う構成なので、対案も **Workers + Supabase Postgres** で比べる。

| 要件 | Workers + **D1** | Workers + **Supabase Postgres** |
|---|---|---|
| R4 `SELECT ... FOR UPDATE SKIP LOCKED` | **無い。** D1 は SQLite であり、この構文を持たない。スケジュール行のポーリング（TECH-00 §4.3）に別の排他方式が要る | **使える見込み。** Hyperdrive は Workers TCP ソケットで Postgres へ接続し、`node-postgres` を推奨ドライバとしている。**接続プーリングは Workers Paid に含まれ追加費用は発生しない**（2026-08-18 取得） |
| 床 | $5 | $5 + Supabase $25 = **$30** |

**この時点で床の差は消える**（主案 $30.9 対 $30）。§9.3 の判断はここを踏まえる。

**要確認（断定しない）**: Hyperdrive 経由で `BEGIN` 〜 `SELECT ... FOR UPDATE SKIP LOCKED` 〜 `COMMIT` が期待通り動くか。Hyperdrive の公開ドキュメントはクエリキャッシュの対象外条件を定めているが、**トランザクションとロックの扱いを明示していない**（2026-08-18 時点）。Supavisor をトランザクションモードで挟む場合の挙動も併せて確認する。動かない場合は Workers TCP ソケットで直結する経路が残る。

### 3.3.1 残る唯一の決め手は R6

| 要件 | 摩擦 |
|---|---|
| **R6 サーバー側の画像処理** | 知覚ハッシュ（TECH-00 §7.1）とバーコードのサーバー側再デコード（§7.3）は **v1 の必須要件**であり、後回しにできない。Workers で画像をデコードするには WASM ライブラリが要り、CPU 時間の制約下に収める必要がある。Python の Pillow / pyzbar / ImageHash に比べて実装コストが明らかに高い |

リサイズはクライアント側で行う（TECH-00 §2 の提案）ため、R6 に残るのは上の2項目である。

加えて、`.agents/rules/` の Python / FastAPI / TDD ルールと、`.agents/skills/supabase-postgres-best-practices/` を捨てることになる（§10）。

### 3.3.2 R1（コールドスタート）では Workers が上回る

§9.4 で Cloud Run をコールドスタートを理由に落としている。**同じ基準を Workers に当てると、Workers は isolate 方式で起動が速く、R1 を主案と同等以上に満たす。** 不採用の理由に R1 を含めない。

### 3.4 提案: Fly.io に単一プロセスを置く

**API・スケジューラ・課金ワーカーを1つのプロセスに同居させる。**

```
Fly.io machine (Python / FastAPI)
 ├ HTTP        : 判定API（同期・R1）、Stripe webhook、静的PWA配信（R12）
 ├ 毎分ループ  : notification_schedule / billing_queue のポーリング（R2）
 └ ワーカー    : 課金実行・メール送信（非同期・R3、並行度を判定と分ける）
```

**理由**

1. **外部サービスの数が最少になる。** 個人開発で最も高くつくのは、壊れる箇所と請求書の数である。スケジューラ専用サービスもキュー専用サービスも要らず、Postgres 1つでスケジュール・キュー・冪等をまかなえる（TECH-00 §4.3）
2. **コールドスタートが無い**（TECH-00 §1-2）。判定 API に起動遅延が乗らない
3. **R6 が素直**。Pillow / pyzbar / ImageHash がそのまま使える
4. **CLI 操作性が高い**。`fly deploy` / `fly secrets set` / `fly logs` / `fly ssh console` で構築から障害対応まで完結する。Dockerfile をビルドしてデプロイするため、**エージェントがローカルで同じイメージを再現できる**
5. **`.agents/rules/python.md` と TDD ルールがそのまま活きる**

**注意**: 単一プロセスに同居させても、**判定と課金の並行度は分ける**（TECH-00 §1-4）。締切時刻の課金バーストが判定のレイテンシを直撃しないよう、ワーカープールを別に持つ。

### 4.2 scale-to-zero は成立しない

TECH-00 §4.3 の帰結。**毎分ポーリングするスケジューラを持つ以上、データベースは常時起動する。**

Neon Free の 100 CU時間は、最小の 0.25 CU が常時起動すると 0.25 × 730 = **182.5 CU時間**となり、無料枠を超える。Neon Launch では 182.5 × $0.106 = **$19.3/月**。

**「サーバーレス DB は使わないときタダ」はこのプロダクトには当てはまらない。** 選定時にこれを前提にしない。

### 4.3 提案: Supabase

**Postgres として使い、加えて認証（R11）も引き受けさせる。**

| 理由 | 内容 |
|---|---|
| **CLI 操作性が最も高い** | `supabase start` で Postgres・Auth・Storage を含む全スタックが Docker でローカルに立つ。マイグレーションは `supabase migration new` で作った**素の SQL ファイル**として git に入る。エージェントが「現在のスキーマを読む → マイグレーションを書く → ローカルに適用 → テストを走らせる」を完結できる |
| 認証を買える | Google / Apple / メール+パスワードの3手段（TECH-00 §3.1.1）と、パスワードリセット・メール確認が揃っている。自前実装すれば数週間かかり、**課金するサービスで認証のバグは高くつく** |
| バックアップ | Pro に日次バックアップが含まれる。自前 Postgres の $2.17 との差 $23 は、1人でこれを運用しないことへの対価と見る |
| 既存資産 | `.agents/skills/supabase-postgres-best-practices/` が既にチェックインされている |

**セッションは自前で包む。** TECH-00 §3.2.1 が「サーバー発行の `HttpOnly` Cookie」を要求しているため、Supabase Auth の発行するセッションを **FastAPI 側で自前の HttpOnly セッション Cookie に包む**。Supabase Auth に任せるのは OIDC のやりとり・パスワードのハッシュ・メール確認・リセットのトークン発行であり、Cookie 層は自分で書く。

### 4.3.1 `auth.users` に課金レコードを従属させない

TECH-00 §8.3.1 は「課金レコードはユーザーレコードへの外部キーに依存して消える設計にしてはならない」と定めている。PRD-05 §5.1 が**未確定の課金がある状態での退会を許可している**ためである。

Supabase Auth を使うと `auth.users` が生まれる。**ここに外部キーを張ったアプリ側のテーブルは、退会時に連鎖して消えうる。** これは実装で必ず踏む。

**設計**

- アプリ側に**独自の `user` テーブル**を持ち、`auth.users` とは**1対1の参照のみ**に留める
- **退会は論理削除**にする（`deleted_at`）。決済に必要な最小限（Stripe の顧客ID、通知先メールアドレス）は課金が決着するまで残す
- **課金レコードは `auth.users` を参照しない。** アプリ側の `user.id` だけを参照する
- 認証情報（`auth.users`）の削除は、未確定の課金がすべて決着してから行う

この保持範囲は削除請求と衝突しうる。**法務確認の対象**（PRD-05 §10 #4）。

**Free から始めて Pro に上げる。** 移行のトリガーは次のいずれか。

- **実際に課金を開始する時点**（バックアップの無い DB で金銭を扱わない）
- ストレージ1GB に到達する時点（写真30日保持で約1GB。§5）

## 8. 開発のしやすさ — CLI と SDK

**2026-08-18 に追加された評価軸**（§0.3）。2つに分ける。

| 軸 | 問い |
|---|---|
| **CLI 操作性**（§8.1〜8.2） | 構築・変更・デバッグ・ローカル再現が**コマンドだけで完結するか**。Web コンソールでしか変更できない設定は、そのままエージェントの手が届かない領域になる |
| **SDK の成熟度**（§8.3〜8.4） | 認証・課金・DB・判定の各層に、**選んだ言語で使える公式クライアント**があるか。無い層は HTTP を手書きすることになり、実装量と事故の確率が上がる |

### 8.1 CLI の評価

| サービス | CLI | できること | 評価 |

| **Fly.io** | `flyctl` | `fly launch` / `fly deploy` / `fly secrets set` / `fly logs` / `fly ssh console` / `fly scale`。**Dockerfile をビルドしてデプロイする**ため、エージェントが手元で同じイメージを再現できる。`fly.toml` が宣言的 | ★★★ |

| **Cloudflare** | `wrangler` | `wrangler deploy` / `wrangler d1 execute` / `wrangler r2 object put` / `wrangler tail`。`wrangler.toml` が宣言的 | ★★★ |

| Vercel | `vercel` | デプロイ・環境変数。§3.2 により候補外 | ★★ |

### 8.2 この軸が選定を動かす2箇所

**(1) Neon より Supabase**

`neonctl` はプロジェクトとブランチしか扱わない。`supabase` はローカルスタック・マイグレーション・型生成・シークレットまで扱う。**エージェントが「現在のスキーマを読む → マイグレーションを書く → ローカルに適用 → テストを走らせる → 本番へ push」を一度も Web コンソールを開かずに完結できる**のは Supabase だけである。

マイグレーションが**素の SQL ファイルとして git に入る**点も大きい。ORM のマイグレーション DSL より、エージェントが読んで差分を判断しやすい。

**(2) `stripe listen` が課金の状態機械の開発を可能にする**

TECH-00 §8.2 の6状態（保留 / 確定 / 失敗 / 中止 / 再審査中 / 返金済み）を実装するには、**決済の失敗・成功・返金を任意に発火できる必要がある**。本番のカードで失敗を再現することはできない。

```
stripe listen --forward-to localhost:8000/stripe/webhook
stripe trigger payment_intent.payment_failed
stripe trigger charge.refunded
```

これが CLI で完結するため、**課金の状態遷移をローカルでテスト駆動で書ける**（`.agents/rules/tdd.md`）。webhook のテストを Web コンソール経由でしか行えない決済サービスであれば、この領域の開発は著しく遅くなる。

### 8.3 SDK の成熟度

主案（Python）と対案（TypeScript / Workers）で、各層に公式クライアントがあるかを並べる。

| 層 | Python（主案） | TypeScript / Workers（対案） |
|---|---|---|
| **決済** | `stripe`（公式）。Stripe の SDK は言語をまたいで水準が揃っており、型・冪等キー・webhook 署名検証が揃う ★★★ | `stripe`（公式）。Workers では fetch ベースの HTTP クライアントを指定する必要がある ★★★ |
| **DB** | `asyncpg` / `psycopg`。**Supabase は素の Postgres なので、Supabase 専用クライアントを介さずに済む** ★★★ | `postgres.js` / `node-postgres`（Hyperdrive の推奨ドライバ）★★★ |
| **認証** | `supabase-py` は `supabase-js` より機能が遅れる。ただし**セッション層は自前で書く**（TECH-00 §3.2.1）ため、必要なのは GoTrue の REST を叩くことだけで、遅れている領域とほぼ重ならない ★★ | `supabase-js` は Supabase の**リファレンス実装**で最も機能が揃う ★★★ |
| **画像判定** | `google-genai`（公式）★★★ | `@google/genai`（公式）★★★ |
| **メール** | `boto3`（公式）★★★ | `@aws-sdk/client-sesv2`（公式、モジュール分割済み）★★★ |
| **Web Push** | `pywebpush` が VAPID 署名と暗号化を実装済み。**そのまま使える** ★★★ | npm の `web-push` は Node の `crypto` に依存し、**Workers ではそのまま動かない**。Web Crypto での再実装（サードパーティ製か自作）が要る ★ |
| **画像処理**（R6） | Pillow / pyzbar / ImageHash。いずれも枯れている ★★★ | WASM 経由。R6 の摩擦そのもの（§3.3.1）★ |

### 8.4 SDK の観点で動く2箇所

**(1) Web Push が対案の新しい摩擦になる**

TECH-00 §5.10 で「Web Push は自前送信で費用ゼロ」としたが、**費用がゼロでも実装がゼロではない**。VAPID の JWT 署名と、ペイロードの ECDH + HKDF + AES-GCM 暗号化が要る。

- Python は `pywebpush` がこれを済ませている
- Workers は npm の `web-push` が Node の `crypto` 前提のため使えず、**Web Crypto での実装を持ち込むか自作する**ことになる

**R6（画像処理）に加えて、R8（Web Push）も対案側の実装コストになる。** §3.3.1 の「残る唯一の決め手は R6」は、正確には **R6 と R8** である。

**(2) Supabase の SDK 差は、セッション設計によって打ち消される**

`supabase-js` が `supabase-py` より成熟しているのは事実で、素直に読めば対案に有利である。**しかし差が大きいのはセッション管理・リアルタイム・ストレージのクライアント側ヘルパーの領域であり、SwitchMe はそこを使わない。**

- セッションは**サーバー発行の HttpOnly Cookie を自前で書く**（TECH-00 §3.2.1）。クライアントのセッション管理は使わない
- DB は**素の Postgres として `asyncpg` で触る**。PostgREST 経由のクエリビルダは使わない
- 残るのは GoTrue（認証）と Storage の**サーバー側 REST 呼び出し**だけで、これはどちらの言語でも同程度である

**結論: この層では両者に実質的な差がない。**

### 8.5 この2軸は主案と対案を分けない

§3.3 で床が同等になった（$30.9 対 $30）ため、CLI と SDK の軸が判断材料として残る。**両方を通しても、決着はつかない。**

| 軸 | 判定 |
|---|---|
| CLI | **引き分け。** `flyctl` も `wrangler` も ★★★、ローカル再現（`docker run` / `wrangler dev`）も両方できる。§3.3 で対案も Supabase を使う以上、**ベンダー数も5つで同数**になり、「対案のほうが単純」は成立しない |
| CLI（細部） | **主案がわずかに有利。** `fly ssh console` で稼働中のプロセスに入って状態を確認できる。Workers にはシェルが無く、`wrangler tail` のログだけになる。エージェントに障害調査をさせる場面で効く |
| SDK | **主案が有利。** Web Push（§8.4-1）と画像処理が Python では既存ライブラリで済み、Workers では実装を持ち込むことになる |

**ユーザーが優先軸として挙げた2つを通した結果、推奨は変わらない。** ただし理由は「対案が劣る」ではなく、**CLI は引き分け、SDK で主案が有利**という内訳である。§8 を追加する前に書いた「この軸では対案が上回る」という記述は、§3.3 で比較条件を揃えた結果、成立しなくなった。

### 8.6 CLI / SDK で扱えない残作業

以下は初回に一度だけ、コマンド以外の作業が要る。**エージェントに任せられない部分として計上する。**

| 作業 | 内容 |
|---|---|
| ドメインの取得と DNS | レジストラの管理画面。DKIM / SPF レコードの追加（SES） |
| Amazon SES のサンドボックス解除 | AWS への申請フォーム |
| Stripe のアカウント審査 | 事業者情報の登録。**「ペナルティ課金」の商品性が審査を通るかは未確認**（§11.2 #7） |

| 画像判定（R7） | **Gemini 2.5 Flash-Lite**、構造化出力 | 従量 $0.6 | — | `google-genai`（公式） |
| メール（R9） | **Amazon SES** | 従量 $0.5 | `aws` | `boto3`（公式） |
| プッシュ（R8） | 自前 Web Push（VAPID） | $0 | — | `pywebpush` |
| 決済（R10） | **Stripe** | 3.6% | `stripe` | `stripe`（公式） |

**床: $5.9/月（Supabase Free 期）→ $30.9/月（Pro 移行後）**

**ベンダーは5つ**（Fly.io / Supabase / Google AI / AWS / Stripe）。うち **Fly.io・Supabase・Stripe は CLI が成熟しており**（§8）、エージェントによる開発・デバッグ・デプロイが完結する。

4つの軸での位置づけ:

| 軸 | 主案の位置 |
|---|---|
| **床** | $5.9 → $30.9。**対案（同条件、$30）とほぼ同じ。床では選べない**（§9.3） |
| **従量** | 100人で月 $1、1,000人で月 $11〜14。再試行が3倍でも床を超えない（§7.4）。**どちらの規模でも床が支配する** |
| **CLI 操作性** | Fly.io / Supabase / Stripe がいずれも ★★★。**対案と引き分け**（§8.5） |
| **SDK の成熟度** | 全層に公式クライアントがある。**R8（Web Push）と R6（画像処理）で対案に勝る唯一の点**（§8.4） |

### 9.2 各層を選んだ決め手（1行ずつ）

| 層 | 決め手 |
|---|---|
| Fly.io | コールドスタートが無く（R1）、常時稼働のスケジューラ（R2）と Python の画像処理（R6）が1プロセスに収まる。外部サービスを増やさずに済む |
| Supabase | `supabase start` でローカルに全スタックが立ち、マイグレーションが素の SQL として git に入る。**エージェント開発で最も操作性が高い** |
| Supabase Auth | 3手段の OIDC / パスワード・`sub` による同一性解決・メール確認・リセットに加え、**検証済みメールに限ったアイデンティティの自動結合が既定で入っている**（TECH-00 §3.3.2）。自前実装で最も誤りやすい箇所を先に押さえてくれる |
| Supabase Storage | v1 の規模では R2 の egress 無料が効かず、ベンダーを増やす理由がない |
| Gemini 2.5 Flash-Lite | 24種のカタログをそのまま扱え、Phase 2 の状態型に地続き。最も安いのは副次的 |
| Amazon SES | **日次上限が無い**（Resend Free は100通/日で課金確定メールが落ちうる）。Resend Pro との差は月 $19 |
| Stripe | PRD で決定済み。国内 3.6%・固定手数料なしで、罰金下限 ¥100 の経済性が成立する |
| Python を選ぶこと | R6（画像処理）と R8（Web Push）が既存ライブラリで済む。**この2つが対案との唯一の差**（§9.3） |

### 9.3 対案: Cloudflare Workers + Supabase（TypeScript）

**同条件で比べる**（§3.3）。対案も Supabase Postgres を使う。D1 を使う構成は R4（`SKIP LOCKED`）を満たさないため、対案として成立しない。

| | 主案 | 対案 |
|---|---|---|
| 床 | $30.9 | **$30**（Workers Paid $5 + Supabase Pro $25。Hyperdrive は追加費用なし） |
| R1 コールドスタート | 満たす | **満たす**（isolate 方式。§3.3.2） |
| R4 `SKIP LOCKED` | 満たす | 満たす見込み（**要確認**、§3.3） |
| CLI | ★★★ | ★★★（**引き分け**、§8.5） |
| SDK | ★★★ | 一部 ★（§8.5） |
| **R6 サーバー側の画像処理** | Pillow / pyzbar / ImageHash | **WASM 経由。実装コストが高い** |
| **R8 Web Push の送信** | `pywebpush` | **Web Crypto での実装を持ち込むか自作** |

**床は実質同じ（$0.9 差）。CLI は引き分け。決め手は R6 と R8 の2つだけである。**

いずれも「できない」ではなく「実装コストが増える」という差であり、**個人開発では自分の時間がそのままコストになる**ため、月 $0.9 の差では覆らないと判断した。

**対案を採る合理的な理由が残る場合**

- TypeScript でフロントとバックを1言語に揃えたい（PWA のフロントは TypeScript になる）
- サーバーを持ちたくない（OS の更新・プロセスの監視が要らない）

このどちらかを重く見るなら、対案は妥当な選択である。**床では選べない。**

### 9.4 検討して採らなかったもの

| 候補 | 不採用の理由 |
|---|---|
| Vercel（Hobby） | **商用利用が規約で禁止**（§3.2）。Pro $20 が床になり、Fly.io より高い |
| Neon | 毎分ポーリングで scale-to-zero が成立せず（§4.2）、Launch で $19.3/月。Supabase Pro $25 と近い額で認証・ストレージ・ローカルスタックが付かない |
