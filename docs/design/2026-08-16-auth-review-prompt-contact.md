# ログイン要否 / 評価の促し / 問い合わせ経路 の意思決定（2026-08-16）

対象ファイル: `docs/design/ui.pen`（本ドキュメントは意思決定の記録。`.pen` はまだ変更していない）

関連画面: `cBFhO` 12 ログイン / `Q19ZMN` 12b 新規登録 / `YuLsu` 26 設定/アカウント / `JSpLI` 65 問い合わせ

---

## 0. 結論

| 論点 | 決定 |
|---|---|
| ネイティブアプリのログイン | **任意**。ログインなしでマイルストーン管理・課金の両方が成立する。ログインは機種変更の引き継ぎと多端末利用のための選択肢として提供する |
| Web アプリのログイン | **最初に必須**。ブラウザには識別子を永続化できる場所がないため |
| 評価の促し | 「初回の7日連続達成」を実績画面で確認した直後を第一候補とし、トリガ側で希少性を担保する |
| 問い合わせ | アプリ内送信を維持し、返信先メールアドレスの行を追加する。メール作成画面への遷移は主経路にしない |

## 1. ログインと認証

### 1.1 決定事項

- **ネイティブ: ログインは任意。** 初回起動時にサーバーが匿名アカウントを発行し、端末が資格情報を保持する。ログイン画面は「機種変更で引き継ぐ」「複数端末で使う」ための任意の経路として残す。
- **Web: 最初にログインを要求する。** マイルストーン作成より前。
- Web の位置情報はバックグラウンド取得を前提としない。**検証を実行する時点で前面から取得すれば足りる**（1.7 参照）。

### 1.2 ログインなしで成立する理由

**課金の実行はサーバー側**である。締切時刻に発火するサーバーのジョブが、保存済みのカードに対して Stripe の off-session で課金する。クライアントから課金を叩く設計は、ペナルティを払いたくないユーザーがアプリを開かなければ回避できてしまうため、そもそも成立しない。またシークレットキーはクライアントに置けない。

一方、カード情報の入力と送信は Stripe SDK（publishable key）でクライアントから直接 Stripe に送る。サーバーはカード番号を受け取らない。PCI DSS の対象範囲を狭めるための正しい構成であり、「フロントで課金しない」とは意味が異なる。

サーバーがマイルストーンの状態・締切・金額・判定を持つ以上、リクエストがどのアカウントのものかをサーバーが判断できる必要がある。これは**認証**の要件であって、ログインの要件ではない。ログインは「ユーザー自身が任意の端末で再現できる資格情報」という一形態にすぎず、端末に保持される資格情報でも認証は成立する。

### 1.3 認証情報の設計

**端末ID（IDFV / IDFA / 端末情報由来の値）を認証情報にしてはいけない。** これらは秘密として設計されておらず、解析すれば任意の値を送れる。これを認証に使うと、他人の識別子を握った第三者が被害者のアカウントに高額のペナルティ付きマイルストーンを作成でき、実際にカードが引き落とされる。加えて写真（洗面台・寝室・入浴後の自撮り）と自宅の位置情報も読める。

採用する構成:

| 要素 | 役割 |
|---|---|
| サーバー発行のランダム秘密トークン（Keychain 保存、同期可） | アカウントの同定。機種変更で引き継がれる |
| App Attest / Secure Enclave 鍵（DeviceCheck、Android は Play Integrity） | 端末バインドの第二要素。トークンが漏れても、正規アプリ・実機からでなければ使えない |

App Attest は鍵ペアを Secure Enclave 内で生成し、秘密鍵はハードウェアの外に出ない。Apple の CA が署名した attestation をサーバーが検証することで「Apple の実機上の、正規のバンドルIDのアプリ」であることを確認できる。第三者が自前で同等のリクエストを作ることはできない。

トークンの取り扱い: アクセストークンは短命にし、リフレッシュトークンと分ける。リフレッシュトークンは使用のたびに回転させ、古いものの再利用を検知したら系列ごと失効させる。ログ・クラッシュレポート・解析SDKに出さない。UserDefaults ではなく Keychain に保存する。TLS に加えて証明書ピンニングを行う。

### 1.4 引き継ぎと漏洩のトレードオフ

一つの仕組みで両方は満たせない。

| 方式 | 盗まれるか | 機種変更で引き継げるか |
|---|---|---|
| Secure Enclave 鍵 | 盗めない | 引き継げない（エクスポート不可・iCloud 同期不可） |
| 同期可能なランダムトークン | 漏洩しうる | 引き継げる |

したがって併用する。トークンで継続性を確保し、attestation で端末を縛る。新端末ではトークンは引き継がれるが attestation 鍵は新規発行になるため、**そこでのみ再確認を挟む**（既存端末での承認、または復旧コード／ログイン）。

これがログイン（または同等の復旧手段）が実際に必要になる唯一の箇所である。必須にはしないが、**引き継ぎを成立させる手段そのものは用意しなければならない**。

> 未確認: アプリ削除時に App Attest 鍵が残るかどうか。**失われる前提**で設計する（削除・再インストールで attestation 鍵は再発行、トークンは Keychain に残る）。実機で確認すること。

### 1.5 ログインを任意にする場合の必須条件

以下がすべて揃って初めて「ログイン任意」が成立する。どれか一つでも欠けると成立しない。

1. **認証情報をサーバー発行の秘密または Secure Enclave 鍵にする**（端末IDを使わない）
2. **被害の上限をサーバー側で決める** — 1マイルストーンあたり・1日あたりのペナルティ金額に上限を設ける。一定額を超える設定と既存マイルストーンの金額引き上げには端末側の生体認証を要求し、**新規作成と金額引き上げは翌日以降の発効**とする。資格情報が完全に奪われても大きな損害が出ないようにするための措置であり、勢いで高額を設定してしまう自傷的な操作の抑止にもなる
3. **一定期間アプリからの通信が無ければ全マイルストーンを自動停止する** — 端末の紛失・破損時の出口。そもそも検証できない以上、未達成として課金する根拠がない
4. **機種変更の引き継ぎ手段を用意する**（1.4）
5. マイルストーンの作成と金額引き上げが起きたら必ずプッシュで通知する

### 1.6 本人による回避への対処は認証では解けない

脅威は2種類ある。第三者による成りすまし（1.3〜1.5 で対処）と、**ユーザー本人による課金回避**である。後者は正規の資格情報を持っているため、認証をいくら強化しても防げない。ルールで防ぐ。

- 判定はサーバーが生の証跡（写真・GPS）から行い、クライアントの「達成しました」は信用しない（現状の設計通り）
- **締切直前のマイルストーン削除・金額引き下げ・一時停止を禁止する。** 8:00 の締切を 7:59 のスワイプ削除で回避できるなら、認証設計に関係なくビジネスモデルが成立しない

`71 オフ期間を選ぶ（当日オフ不可）` で一時停止についてはこの原則が入っている。**同じルールが削除（`01c` / `72b` の引き切り削除、`16` 削除確認）と金額変更にも適用されているかを確認すること。**

### 1.7 Web で最初にログインが必要な理由

ブラウザには識別子を永続化できる場所がない。Safari の ITP により、サイト未訪問が数日〜1週間続くと localStorage も Cookie も破棄される。消えた時点でユーザーはサーバー上の自分のアカウントに到達できなくなり、カードを外すことも退会することもできない。一方で**課金処理はサーバー側なので動き続ける**。これが最悪の組み合わせであり、Web で遅延の余地がない理由である。

**位置情報について（決定）**: Web ではバックグラウンド取得を行わない。検証を実行する時点で前面から Geolocation API で取得すれば要件を満たす。これは前提として確定。

これに伴う帰結を2点記録しておく。

- **自動達成は Web では提供されない。** 仕様書の `46 バックグラウンド検証通知`（位置情報で自動達成した際の通知）はネイティブ専用の機能になる。Web ではユーザーが締切前にアプリを開いて検証を実行する必要がある。
- **リマインダーの到達性が落ちる。** iOS のブラウザでプッシュ通知を受け取るには、ユーザーがホーム画面に追加した PWA である必要がある。通常のタブで開いているだけでは通知が届かない。締切前の催促が機能しないと未達成率が上がり、課金が意図せず増える方向に働くため、Web を出す場合は PWA インストールの導線が実質的に必須になる。

## 2. 評価の促しをどこで出すか

### 2.1 API の制約から設計が決まる

- iOS のレビュー要求は **StoreKit の `requestReview` を使うことが必須**で、自前のダイアログでレビューを求めることは認められていない。
- 表示は **1ユーザー・1アプリあたり 365日で最大3回**にシステム側で制限される。
- **呼び出しが実際に表示されたかどうかをアプリ側から知る方法がない**（レーティング内容も不明）。

3点目が設計上いちばん効く。システム側の制限に頼って「とりあえず毎回呼ぶ」と、どこで3回を使い切ったかを自分で把握できない。したがって**トリガ条件そのものが構造的に希少でなければならない**。

### 2.2 候補の評価

| 候補 | 年間の発火回数 | 判定 |
|---|---|---|
| 46 検証結果（達成）の直後 | 数百回 | ✕ 使えない。加えて起床直後・ジム内・カメラ操作中と、いずれも慌ただしい文脈 |
| 01d ホーム（今日の全件完了） | ~365回 | ✕ そのままでは使えない |
| 週次サマリ「今週の未達成0 / 課金 ¥0」 | ~52回 | △ 「初めての完璧な週」など明示的に絞れば可 |
| **初回の7日連続達成** | 1回 | ◎ 構造的に一度きり |
| 30日 / 100日連続達成 | 各1回 | ◎ |
| 異議申し立てが通った / 返金された直後 | 稀 | ✕ こちらの誤判定を認めた直後にレビューを求めることになる |
| オンボーディング完了直後 | 1回 | ✕ まだ価値を受け取っていない |

### 2.3 推奨する3枠の割り当て

1. **初回の7日連続達成** — 04 実績画面を開いて数値を確認した後
2. **初回の「課金 ¥0 の月」の月次サマリ表示時**
3. **30日連続達成** — 同じく実績画面で

いずれも「達成した瞬間」ではなく**実績画面で自分の成果を見ている状態**で出す。このアプリの満足の実体は個々の達成ではなく「自分が続けられている・課金されていない」という累積の確認であり、それが可視化されるのは実績画面だからである。実績画面は締切に追われていない落ち着いた文脈でもある。

### 2.4 除外条件（アカウント単位で判定する）

マイルストーンAで7日連続を維持しながら同じ日にマイルストーンBで課金される、ということが普通に起きる。ストリークだけでは満足を意味しない。以下のいずれかに該当する場合は条件を満たしていても**呼ばない**。

- 直近14日以内にペナルティ課金が1件でもある
- 未クローズの問い合わせ（65）または異議申し立てがある
- 支払い失敗・カード期限切れ状態にある（20 / 50）
- 直近7日以内に検証失敗（45 / 46b）がある
- 当日の朝の締切時間帯（例 6:00–9:00）である

### 2.5 「評価する」ボタンは別物として設定に置く

`requestReview` はユーザー操作に応じて呼ぶべきではない（表示される保証がなく、何も起きない体験になる）。設定（11）またはヘルプ（28）に「App Store で評価する」の行を置き、`https://apps.apple.com/app/id{APP_ID}?action=write-review` を直接開く。2.3 のプロンプトとは独立した経路として扱う。

### 2.6 画面への影響

新規画面は不要（システムダイアログのため）。ただし以下を追加する。

- 04 実績に「月次サマリ」の表示（2枠目のトリガ条件がまだ画面上に存在しない）
- 11 設定 または 28 ヘルプに「App Store で評価する」行

## 3. 問い合わせをどう受けるか

### 3.1 現状の画面が既に約束していること

65 問い合わせ（`JSpLI`）の現状は次の構成になっている。

```
種類（課金のこと / 検証のこと / その他）
関連するマイルストーン（任意）  … 「ジムでトレーニング · 8月5日」
内容（自由記述）
スクリーンショットを添付
通常2営業日以内に登録メールアドレスへ返信します
[送信する]
```

ここから2つのことが言える。

1. **この画面は実質的に課金の異議申し立て窓口になっている。** 仕様書にある `47 異議申し立て／再審査依頼` は `.pen` にまだ存在せず、「種類=課金のこと」＋「関連するマイルストーン」が、ユーザーが課金に反論できる唯一の経路である。
2. **画面は既にメールで返信すると宣言している。** つまり論点は「2つの新しい設計のどちらを選ぶか」ではなく、**すでにした約束の裏付けが無いのをどう埋めるか**である。

### 3.2 「メール作成画面へ飛ばす」案の評価

手間が少ないという見立ては、**送信側（ユーザー）の手間**については正しいが、**全体の手間**では成り立たない。

- 構造化フィールド（種類・マイルストーンID・課金ID・アプリバージョン・OS・端末）は、メール本文にテキストとして流し込むしかない。ユーザーは消せるし、実際に消す。結果として問い合わせのたびに「どの課金の話ですか」と往復が発生する。**手間が消えるのではなく、返信インフラの構築コストが手作業のトリアージに移るだけ**である。
- 課金IDと問い合わせがサーバ上で紐づかない。チャージバックや返金対応の際に、「いつ誰が何に異議を出したか」の記録がこちら側のメールボックスにしか無い状態になる。
- 端末にメールアカウントが未設定だと詰む。iOS では Mail アプリが削除されている場合やアカウント未設定の場合、メール作成画面を開けない。
- スクリーンショットの添付は `mailto:` URL では不可能。ネイティブのメール作成コンポーザ（`MFMailComposeViewController`）なら添付できるが、それはもう「メールアプリへ飛ばす」ではなく実装が必要な経路になる。
- Web では `mailto:` の挙動がブラウザ・OS 設定に依存し、デスクトップでは何も起きないことがある。

### 3.3 ログイン手段ごとの「返信先メールの有無」

| ログイン手段 | 返信可能なアドレス | 備考 |
|---|---|---|
| メール + パスワード | あり | — |
| Google | あり | — |
| Apple（メール共有） | あり | — |
| Apple（メールを非公開） | あり（条件付き） | `@privaterelay.appleid.com`。**送信元ドメインを Apple Developer の Email Communication に登録し、SPF レコードを公開している場合のみ**届く |
| X | **無い場合がある** | X の OAuth はメールを返さない設定がありうる |
| **未ログイン（匿名）** | **無い** | ネイティブでログイン任意にした結果、これが多数派になりうる |

最後の行が今回の決定によって新たに効いてくる。**ログインを任意にした以上、返信先メールを持たないユーザーが標準になる**ため、問い合わせ画面でのメール入力の重要性は当初の想定より上がる。

### 3.4 決定

**アプリ内送信を主経路として維持し、返信先メールアドレスの行を 65 に追加する。**

- アカウントに有効なメールアドレスがある場合は、その値を表示して**編集可能な1行**にする（入力不要）。
- アドレスが無い場合（匿名・X のみ連携）は、**必須入力**にする。
- 送信はアプリ内 API でサーバに保存し、`charge_id` / `milestone_id` / アプリバージョン / OS / 検証時の証跡（写真・GPS ログ）を自動で紐づける。返信はメールで行う。
- 「返信不要のフィードバック」と「返信が必要な問い合わせ」を種類で分け、前者ではメール欄自体を出さない。
- **メール作成画面へのフォールバックを残す**: 送信 API が失敗したときに「メールで送る」ボタンを出し、構造化内容を本文にプリフィルしたコンポーザを開く。加えて 28 ヘルプ・29 利用規約にサポート用アドレスを明記する（特定商取引法の表示としても必要）。

### 3.5 他の選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | アプリ内フォーム + 返信先メール欄（**採用**） | 構造化データを保持しつつ返信経路を確保できる。追加コストは1フィールドとメール送信基盤のみ |
| B | メール作成画面へ遷移 | 3.2 の通り。フォールバックとしてのみ採用 |
| C | サポートSDK の導入（Zendesk / Intercom / Helpshift 等） | アプリ内スレッド + プッシュ返信まで一式入る。月額費用と SDK 依存、課金IDの自動紐づけは自前実装が必要 |
| D | アプリ内インボックスで返信を返す（メール不要） | **課金に怒って即アンインストールしたユーザーに返信が届かない**。単独では採用しない。A との併用なら有効 |
| E | Web フォームをブラウザで開く | 実装は最小。ログイン状態と証跡の受け渡しが切れ、A の利点を失う |

段階的に進めるなら **A を実装 → 反響が増えたら D を足す → 運用が回らなくなったら C** の順。

## 4. 要確認事項

- **ペナルティ課金を App Store 配信アプリから外部決済（Stripe 等）で行えるか。** デジタルコンテンツの購入ではないため IAP 対象外と解釈できる余地はあるが、審査で通る保証はない。ここが覆るとログイン・カード登録・問い合わせのすべてが影響を受けるため最優先で確認する。本ドキュメントでは判断していない
- アプリ削除時に App Attest 鍵が残るか（1.4）。実機で確認する
- 締切直前の削除・金額引き下げが禁止されているか（1.6）
